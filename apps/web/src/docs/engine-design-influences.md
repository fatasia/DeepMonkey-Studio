# 引擎借鉴与设计理念

这篇文档说明 Deep Engine 从 Unity、Babylon.js、Bevy、Godot 学到了什么，以及这些思路如何落成自己的 WebGPU、Native、Deep 2D 与 GUI 架构。它记录设计来源，不代表兼容这些引擎，也不把参考对象自动列为性能对手。

## Unity：作者体验与可检查配置

我们借鉴 Unity 的组件化场景、Inspector、材质与质量档位：对象能力应由清晰组件组成，可编辑参数应集中出现在属性面板，材质、灯光、相机和后处理都要能恢复默认、保存预设并支持撤销。渲染配置使用 `auto → 项目预设 → 场景覆盖 → 对象覆盖` 的继承顺序，让默认画面直接可用，同时保留细粒度控制。

Deep Engine 没有复制 Unity 的 MonoBehaviour、序列化格式或渲染管线。Studio 的作者状态先编译成稳定运行合同，再投影到 Three 作者画布、Deep WebGPU 和 Deep Native。这样可以保持对象身份、发布诊断和三端一致性，也避免把编辑器内部对象直接暴露为运行时 API。

## Babylon.js：Web 优先与渐进能力

我们借鉴 Babylon.js 对浏览器设备能力、场景资源、帧图、实例化和调试工具的重视。WebGPU 能力必须在运行时探测，缺少某项特性时给出明确回退或阻断；关闭的效果不得继续占用无贡献 pass、attachment 或显存。大场景通过稳定实例、资源复用、驻留预算与按需渲染降低每帧固定成本。

Deep Engine 的 Web 路径与 Native 路径共享内容身份和质量要求，但不强求执行细节相同。浏览器使用适合 WebGPU 的异步加载和宿主帧循环，Native 使用 wgpu、系统媒体和原生窗口能力。两端都必须通过同一发布能力检查。

## Bevy：插件、资源与可调度阶段

我们借鉴 Bevy 的 App、Plugin、Resource 和 schedule 思路。`DeepApp` 是独立宿主，插件声明依赖、提供带类型资源、注册帧阶段，并在失败或退出时逆序释放。渲染侧把提取、准备、上传、可见性、编码和提交拆成可测阶段，避免一个巨型主循环掌握所有状态。

我们没有照搬完整 ECS。作者场景、二维文档、图表和工业对象已有稳定领域模型；强行改成一种组件存储会增加同步成本。Deep Engine 在高频执行数据上使用稳定 slot、紧凑缓冲和增量 change set，在产品语义层保留清晰对象与事务。

## Godot：场景组合与强 GUI

我们借鉴 Godot 的 Scene/Node 组合、资源复用、信号式交互，以及 GUI 对布局、焦点、主题和输入的完整建模。Deep GUI 采用保留式控件状态与统一事件语义，目标是让按钮、输入框、文字、图片、视频、下拉选择、表格和图表在 Web 与 Native 中保持布局、字体、色彩、焦点、IME、剪贴板、滚动、DPI、键鼠和触控行为一致。

Godot 只作为产品与架构研究来源。它不进入本轮性能排名、能力分母或下载安装清单。

## Deep Engine 自己的分层

1. **作者层**保存项目、场景、二维页面、工业语义和撤销事务。
2. **编译层**把作者内容冻结为 RenderPacket、Deep 2D display list、资源清单与目标能力报告。
3. **执行层**由 Deep WebGPU 或 Deep Native 消费同一身份与配置合同，并采用各自后端的最佳执行方式。
4. **宿主层**负责窗口、Canvas、帧循环、输入、文件、网络凭据与生命周期。
5. **扩展层**通过 `DeepAppPlugin`、带类型资源和公开子路径 API 接入，不依赖 Studio 私有源码。

核心原则是复用现有生产能力、失败关闭、增量更新和证据先行。新模块必须有真实消费者；新配置必须有默认值、显式覆盖、继承来源和诊断；性能优化必须在同内容、同画质、同设备下测量，不能依靠关闭效果或删减功能取得数字。

## 零配置与高度可配置如何共存

设计目标是让默认配置根据设备能力、场景负载和质量目标选择经过验证的预设。用户不配置时应得到完整光照、材质、色彩、抗锯齿和资源预算；用户需要控制时可以锁定单项，并查看该值来自自动决策、项目预设、场景还是对象。显式值不会被自动调节悄悄覆盖，设备不支持时会显示原因与实际回退。尚未完成生产接线的高级 GI、光追和材质扩展仍以能力报告为准。

API 与接入方式参见 [Deep Engine 独立 SDK](deep-engine-sdk)。真实性能结论参见 [引擎性能与画质基准](engine-benchmarks)。
