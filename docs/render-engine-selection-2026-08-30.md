# 渲染引擎路线决策（2026-09-11：自研 Orillusion 升级路线）

## 决策状态

2026-08-30 的“Three.js 单引擎路线”已被 2026-09-11 的产品决策取代。本文只保留决策记录，不再作为现行架构约束执行。

## 当前决策

产品启动基于 Orillusion 的自研 WebGPU 引擎路线，目标是在可度量的性能、画质、能力和工程治理门槛上超越 Three.js 与 Babylon.js 在 Deep Monkey Studio 场景中的表现，并逐步作为实验引擎替换 Three.js。

该路线允许多引擎并存、对比与迁移：

1. Three.js WebGL 2 / WebGPU 继续作为生产基线和兼容性参照，不因自研路线启动而立即移除。
2. 自研 Orillusion 升级引擎进入独立实验轨道，先通过引擎中立 Scene SDK、影子模式、同画质基准和回归门禁，再进入项目试点。
3. Babylon.js 作为能力参照与竞争研究对象，不因旧策略禁止其出现在调研、基准或能力矩阵中；但是否引入 Babylon 运行时依赖必须由具体实现需求决定，不得仅为移除旧策略而添加依赖。
4. 渲染基准必须覆盖 Three WebGL 2、Three WebGPU、自研引擎 WebGPU，原生客户端可用后还应加入 native runtime；Unity / UE5 / Godot 仅作为外部参考基线。
5. 高级能力优先沉淀到自研引擎核心与 Three 兼容层，不以“增加可选后端”为名复制产品功能，也不允许绕过架构评审、合同测试、视觉验收和性能门禁。

## 与旧决策的关系

旧决策中的“放弃 Babylon、不建设双引擎、主渲染固定 Three.js、禁止 Babylon 依赖、仅比较 Three WebGL/WebGPU、更换主渲染必须重新立项”限制全部废止。双引擎阶段的维护成本是现实风险，必须通过清晰分层、共享 Scene SDK、单一产品语义和证据门禁控制，而不能通过禁止对比来掩盖。

## 后续要求

具体架构、兼容策略、原生客户端、GUI / 图表、路线图和验收门槛见《自研 WebGPU 引擎路线报告》。在实验引擎通过产品级影子运行、同画质回归、性能与恢复门禁之前，生产默认引擎不变。
