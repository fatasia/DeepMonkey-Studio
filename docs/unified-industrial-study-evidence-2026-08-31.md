# 统一工业 Study 收口证据（2026-08-31）

## 结论

Plant Lite、What-if、工位体检和虚拟调试已经进入同一个可追溯 Study 索引。统一层只从各能力的权威持久化记录派生，不复制结果、不新增求解器、不增加一级导航。

这不是通用 PLM/审批平台。它解决的高价值问题是：一次工况运行后，用户能确认“用了什么输入、哪个引擎版本、针对哪个场景/模型、结果和证据是什么”，并能从同一入口对比或复验。

## 改造前核对

| 能力 | 原有完整证据 | 原有缺口 |
|---|---|---|
| Plant Lite | 输入、seed、重复次数、执行引擎、95% 区间、终止状态、精确复现 | 与其他验证结果分表展示 |
| What-if | 完整输入、输入/结果指纹、适用域、风险、引擎版本、精确复现 | 与其他验证结果分表展示 |
| 工位体检 | 场景/对象、目标、最近结果、结果指纹 | 没有保存完整体检输入、引擎/场景/模型版本证据；重复运行覆盖最近结果 |
| 虚拟调试 | 场景/对象、目标、最近结果、结果指纹 | `manual` 类型含义模糊；没有保存场景/黄金矩阵输入和版本证据；重复运行覆盖最近结果 |

## 当前合同与持久化

- `IndustrialStudyRecord` 统一表达类型、工况输入、场景/模型/版本指纹、执行引擎、运行终态、结果摘要、证据、基线谱系和复现入口。
- 原始 Plant Lite、What-if 和 `IndustrialValidationStudy` 仍是唯一持久化源；`OperationsService.snapshot()` 只生成派生 `studies`，避免双写漂移。
- 新的工位体检与虚拟调试记录保存完整可序列化输入。输入指纹由 API 根据收到的实际 JSON 重新计算，页面传入的场景/模型指纹只用于发现工程上下文变化，不冒充防篡改签名。
- 工位体检和虚拟调试每次完成创建一条新记录，并用 `baselineStudyId` / `reproductionOf` 连接前一次结果；准备态任务卡仍可保留。
- 旧 `manual` / `maintenance-diagnosis` 任务卡仅因历史入口都在虚拟调试台而兼容归类为 `virtual-commissioning`。旧记录缺什么就显示什么为缺失，不补造输入、模型或场景证据。

## 页面闭环

统一历史区位于现有 Operations 内容区下方：

1. 按物流仿真、What-if、工位体检、虚拟调试筛选运行历史。
2. 查看结果摘要、关键指标、输入/场景/模型/结果指纹和已保存工况 JSON。
3. 选择同类型基线，对比输入、场景、模型、引擎版本和结果证据是否一致、变化或缺失。
4. Plant Lite / What-if 复用现有精确复现 API；工位体检 / 虚拟调试回到现有虚拟调试工作台；有关联对象时可直接定位 3D。

## 自动化证据

- API：统一投影覆盖四类记录、基线谱系、权威输入持久化、服务重启恢复和旧记录缺失语义。
- Web：统一历史 UI、五类证据对比、工作流动作路由、场景/模型/版本指纹稳定性、工位体检与虚拟调试新记录谱系。
- 文件规模：新增实现均不超过 300 行；既有 `OperationsCenter.tsx` 和 `VirtualCommissioningWorkbench.tsx` 保持低于 800 行硬门槛。

## 已知边界

- 当前运行均为同步请求或插件调用，统一索引保存最终状态；`running/cancelling` 已进入合同，但未为此引入任务队列。
- Plant Lite / What-if 的权威记录没有独立模型指纹，因此统一层严格返回 `model: null`，不能把工况输入哈希改名成模型证据。
- 场景/模型指纹用于版本漂移检测，不是数字签名。需要抗抵赖时仍应由部署侧审计日志、账户和制品签名提供。
