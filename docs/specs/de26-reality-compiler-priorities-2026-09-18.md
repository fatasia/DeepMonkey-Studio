# DE26 收益排序与 Reality Compiler 定位

最新画质决议：**效果先抓光照、材质和稳定性；Three/Babylon 对照工程实现，Unity/UE 对照系统设计与视觉目标。** 多灯、GI、模型受光及阴影联动不是可选装饰，按 [Unity 能力对齐方案](de26-unity-lighting-parity-2026-09-18.md) 补入现有 E 卡并逐格验收。下文的投入排序不得用于裁掉这些已确认能力。

2026-09-18：把工程模型和现场数据编译成可验证、可交互、可离线交付的工业应用，是 Deep Monkey Studio 值得集中投入的方向。Reality Compiler 可作为这条路线的战略名称；客户类别名称用“工程数据编译与运行平台”。

本评审承接用户最新指令，不沿用原研究稿的范围限制。投入排序来自现有代码、交付依赖和客户任务的判断，不是市场规模测算或已实现收益。新增任务没有纳入当前完成率。当前三条收尾线持续执行。

V11 的最新用户要求是**在场景里拖拉拽搭建**，不是提供独立建模工具。具体模板族、贴地/吸附、连续铺设、撤销与保存发布验收见 [场景搭建素材库](de26-v11-scene-building-assets-2026-09-18.md)。

推进顺序：先闭合 C07/C08 来源与变更链、B03/B05 运行预算、G06 数据版本，再让 H02/H09 和场景补齐消费它们。分支按依赖并行，不以所有基础卡全部结束作为可以开始验证的前提。

## 先修正报告的判断

| 原判断 | 本次校准 | 对执行的影响 |
|---|---|---|
| 编译端天然没人占，CAD 与渲染没有交集竞争者 | Unity Asset Transformer 已做 CAD/BIM 导入与优化，NVIDIA Omniverse 有工程数据接入、验证和场景工作流 | 竞争点必须落在使用成本、可追溯性、具体格式 profile、离线交付和变更维护效率 |
| Deep 只是 Three 下的渲染后端，交互层为零 | Web 存在 Three 桥接；Native 已有自己的窗口、拾取、坐标和运行包路径 | 分开描述 Studio、编译链、Web 桥和 Native 运行时，不拿单一路径代表全产品 |
| Native 没有 floating origin，只有基础阴影且无多灯基础 | 已有重基点 GPU/拾取测试、CSM、局部阴影、cluster grid；覆盖与生产接线仍要逐项验收 | 做连续重基点、稳定性、预算与双端传递，不重造已存在的模块 |
| 有 Frame Graph 就等于生产管线接通 | 声明图、执行计划、实际提交和 GPU 输出是不同证据 | B03 验收必须追到真实提交，不能只统计模块或单测 |
| BIM 天然精确，是唯一可靠现实依据 | CAD、GIS、点云、传感器和测量也提供证据；BIM 自身会过期、缺项或单位错误 | 保留来源、坐标、精度预算、时效、置信与缺失状态，不把模型当事实本身 |
| 本地离线必然更便宜，未来十八个月存在竞品真空 | 成本取决于终端、并发、更新频率和运维；版本路线不等于市场退出 | 用实际部署成本与更新任务测量，不把预测当商业承诺 |

本地依据：`lighting/clusterGrid.ts`、`webgpu/pbrFrameGraph.ts`、`webgpu/pbrFramePlanExecutor.ts`、`shaderAuthoring/packageAdapterCsm.ts`、Native `renderer/coordinate_frame_gpu_tests.rs` 与 `player_picking_world_tests.rs`。这些路径证明基础实现存在，不替代全场景验收。

官方竞品依据：[Unity Asset Transformer](https://unity.com/products/unity-asset-transformer)、[Asset Transformer SDK](https://docs.unity.com/en-us/asset-transformer-sdk/2026.4)、[NVIDIA Omniverse](https://docs.nvidia.com/omniverse/index.html)。这些是定位比较，不是引入商业运行依赖的方案。

## 投入排序：先减少交付和维护成本

| 顺位 | 能力与客户收益 | DE26 归属 | 本轮最小可验收结果 | 主要成本/风险 |
|---|---|---|---|---|
| 1 | 可追溯编译：知道哪个源构件为什么缺失、变形或降级，减少人工查错 | C08 + H02 | SourceBundle→稳定构件 ID→几何/材质/运行对象的 source map；质量报告可定位源对象 | 多格式语义差异；复用工业线，禁止另起解析器 |
| 2 | 增量构建和更新：一次小改动不用全量重发，缩短维护周期 | C07 + H07 | 受影响产物集合、缓存键和 delta 可解释；候选真正呈现后才切换 LKG | 并发、断电、坏缓存、运行时版本兼容 |
| 3 | 二维三维共用数据版本：看板、设备状态与告警不会各说各话 | G06 + G08 | 同 revision、单位、时间戳和 stale 状态；记录并回放一次数据更新 | 权限、乱序、旧数据被误认为实时 |
| 4 | 真实运行图和资源账本：把已有 GPU 能力用起来，减少卡顿与显存峰值 | B03 + B05 + H03 | 实际 pass 对应计划；新旧候选同时驻留的峰值和上传预算可查 | 不能用 FPS 提升掩盖画质或内容退化 |
| 5 | 有边界的 agent 编辑：批量查找、改属性和状态绑定，降低重复操作 | 新 H09，复用 H02/H07 | 先输出计划与 diff，校验后事务提交；失败回滚，完整操作记录 | 错对象、过期 revision、越权与过大批量 |
| 6 | 工业场景光照/材质可携带：Web 调好的场景离线仍可用 | E02 + E05 + C04/C05 | 环境/曝光/支持灯光和材质语义进入包；不支持字段明确诊断 | 不追全套 OpenPBR/TSL/Substrate；优先真实样本高频字段 |
| 7 | 大坐标和持久标注：跨建筑移动与检修标记不漂移 | D04 + D05 | 连续重基点、世界坐标持久化、单位变换和恢复保持误差预算 | 局部顶点精度与源坐标精度要分账 |
| 8 | 可复现交付：问题包能还原版本、资源和操作轨迹 | A02/A03/A08 + I07 | 冻结真实资产、版本、轨迹、原始指标和脱敏复现包 | 缺少某引擎/某通道证据时保持未验证 |

前四项是首批收益来源；第五项只做现有命令能力的受限封装，不先造聊天界面。第六至八项按当前交付的缺口穿插，不等全部架构完成再验证。机器任务清单的 `strategy20260918` 保存每卡新增验收要求；原验收仍有效。

## 报告的新功能，哪些值得拿

- 多灯、CSM、GPU-driven：拿生产接线、预算、稳定性和真实灯阵验证，避免重复购买已有代码的开发成本。
- 材质标准：拿统一中间语义、明确降级和常见 glTF 字段，不先做完整材质语言或无限节点编辑器。
- Agent/MCP：拿可读、可计划、可校验、可回滚的事务接口。自然语言只是调用端，不是可靠性机制。
- HTML-in-3D：优先让现有 DOM/Deep2D 信息牌共用构件 ID、遮挡与事件规则；只有真需求需要 HTML 纹理时才加后端。
- 程序化园区环境：已批准 V11，复用已有参数化/预制件能力，只补真实道路、围栏、绿化等模板缺口；不做通用世界生成器。
- V12 不做：不新增扫描现场对照或 Splat 试验，不引入相关依赖。地球级相机与完整材质图继续暂缓，既有工业点云/Tiles任务保留原范围。

## Reality Compiler：适合，但不能单独承担全部解释

它的优点是记忆点强，能串起解析、优化、语义、数据绑定和双端发布，也能解释为什么不是又一个大屏编辑器。缺点是“现实”大于我们的实际输入：容易被理解为扫描重建、生成世界、物理仿真或对现实正确性的保证；“编译器”对业务客户也不够直观。名称独占性和商标未做结论。

建议三层表达：

| 场合 | 表达 |
|---|---|
| 产品品牌 | Deep Monkey Studio |
| 客户类别 | 工程数据编译与运行平台 |
| 战略签名 | Reality Compiler · 现实编译器 |

一句话：**把工程模型和现场数据编译成可验证、可交互、可离线交付的工业应用。**

英文：**Compile engineering data into runnable industrial worlds.**

Deep Engine 保持运行时名称；Deep2D 是二维表达与交互能力；Reality Compiler 描述 Studio 内的编译链及整体产品方向，不把渲染器改叫编译器。`three-mesh-bvh` 是空间加速库，不是场景图或“目标机”。

真正应落地的编译契约：

```text
SourceBundle（来源、hash、版本、单位、边界）
  → 语义场景 IR + source map + 质量诊断
  → 规范化 RenderPacket / 数据绑定 / 派生资产
  → Web / Native 目标适配与能力校验
  → 不可变发布包 → 候选呈现 → 原子切换或回滚
```

这是目标架构与已有模块的组织方式，不宣称当前所有格式已贯通。来源未知、缺失、过期或低精度必须进入诊断；不能靠编译消除输入事实的不确定性。

## 商业切入与结果指标

优先服务有持续模型变更、设备数据接入和内网交付需求的工业集成商及工程运维团队。首个可卖结果是“从模型到可维护的交付包”，不是卖自研渲染算法数量。对外演示用一次真实模型更新：保留构件身份与绑定，只重建受影响资产，发布失败可回到旧版本。

建立基线后比较同一项目的首次可交互耗时、人工修复时长、单次变更重建/传输量、源对象可追溯覆盖率、失败恢复成功率与终端运行预算。指标来源和分母固定；未测不写百分比，不预设离线方案一定胜出。

六小时收尾线继续执行：当前实现优先提供上述指标的可信输入，DE26 增强的规模和完成状态单独列账。下一项设计决策应由这组结果驱动，而不是由“现实编译器”这个名字倒逼堆功能。
