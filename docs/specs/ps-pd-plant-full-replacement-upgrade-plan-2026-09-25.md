# PS / PD / Plant 全面平替升级方案

日期：2026-09-25  
目标：在 Deep Monkey Studio 内形成可替代 Siemens Process Simulate、Process Designer / Teamcenter Manufacturing、Plant Simulation 的统一工业数字线程产品，并保持场景内、可追溯、可复现和易上手。

## 1. 产品目标

目标产品不是三个独立软件的拼盘，而是一个统一工作台：

```text
产品/工艺数据
    ↓
场景与资源建模
    ↓
物流/工艺/机器人/控制仿真
    ↓
实验、优化、验证、变更分析
    ↓
报告、作业指导书、执行端发布
```

用户始终围绕同一个项目、同一套对象 ID、同一套版本和同一套 Study 工作，不在多个孤立软件之间复制模型。

首版完整替代范围：

- 离散制造与物流建模、运行和统计分析；
- 机器人工作单元、运动、碰撞、可达性和节拍验证；
- PLC/IO/机器人控制器的虚拟调试；
- EBOM、MBOM、BOP、BOE、工序、资源和作业指导书；
- 试验设计、参数优化、方案对比、置信区间和可审计报告；
- 从 CAD/BIM/工业格式导入到场景、仿真和发布的可追溯链路。

不把“支持所有行业、所有机器人品牌、所有 CAD 私有版本、认证级动力学”作为同一批次承诺；这些采用 profile 和插件逐步扩展。

## 2. 现状核查与复用原则

### 已有能力（不重建）

- `plant-lite-simulation`：离散事件、生产订单、多品种、班次、故障、换型、预热、重复实验、置信区间、质量、能耗和轨迹。
- `factory-flow-plugin`：轻量场景内快速建模与播放入口。
- 场景仿真面板、稳定场景对象 ID、场景保存/恢复、Study 记录和时间线桥接。
- 工位/机器人、虚拟调试、Rapier 物理、AGV 运动、PPR/BOP 和 Operations 体系。
- 插件运行时、Data Hub、统一转换任务、格式质量报告、源文件哈希和发布审计。

### 升级原则

1. Plant Lite 继续作为过程仿真真值内核，不新建第二套 DES。
2. `SimulationStudyDocument`、`IndustrialStudyRecord` 和场景稳定 ID 作为统一真值，不在各面板保存副本。
3. 3D 只消费仿真事件和轨迹；渲染帧率不得改变正式仿真结果。
4. 物理、机器人、控制、物流采用不同求解频率，但共享时间协议、坐标帧、对象 ID 和回放证据。
5. 所有新能力先做合同、黄金样例和失败证据，再做 UI 扩展。

## 3. 统一领域模型

新增或收敛以下核心对象：

```text
ProductDefinition     产品、变型、配置、EBOM
ManufacturingProcess   工艺路线、工序、前置关系、标准工时
ResourceDefinition     设备、机器人、人员、工具、输送、AGV、PLC
SceneBinding           场景对象、几何、坐标、碰撞体、运动学绑定
SimulationStudy        输入、时间、分布、资源、实验矩阵、随机种子
ControlScenario        PLC/IO/控制器、信号、时序、故障注入
ValidationCase         碰撞、可达性、节拍、安全、安装、质量门禁
StudyResult            指标、轨迹、日志、证据、统计、报告和谱系
ReleaseBaseline        发布版本、审批、签名、回滚和执行端包
```

每个对象必须有：`stableId`、版本、来源、单位、坐标帧、状态、权限、变更记录和可追溯引用。删除对象时只允许进入断链诊断，禁止静默改绑。

## 4. 技术架构

```text
Studio Core
├─ Scene / Asset / Data Hub / Plugin Runtime
├─ Manufacturing Digital Thread
│  ├─ Product / EBOM / MBOM / BOP / BOE
│  ├─ Change / Variant / Baseline / Permission
│  └─ Study / Evidence / Release
├─ Simulation Runtime
│  ├─ Plant DES Worker
│  ├─ Robot Kinematics + Collision Worker
│  ├─ Physics Worker
│  ├─ Control / PLC Co-simulation Adapter
│  └─ Experiment / Optimization Scheduler
└─ Scene Capability SDK
   ├─ Paths / Tracks / Heatmaps / KPI HUD
   ├─ Robot playback / collision overlay
   ├─ Signals / alarms / timeline
   └─ Selection / drill-down / report links
```

运行层统一采用 `SimulationEnginePort`：`validate → prepare → run → progress → cancel → result → trace`。浏览器、桌面和服务端分别使用 Worker、Tauri sidecar 和 `worker_threads` 适配器；不把 Node、Three 或 React 引入仿真核心。

## 5. 四类仿真内核

### 5.1 Plant：离散事件与物流

第一批对象：Source、Sink、Process、Assembly、Batch、Buffer、Store、Conveyor、Track、Transfer、Merge、Split、ResourcePool、Worker、AGV、Forklift、Rack、Pallet、Kanban、Shift、Failure、QualityGate、Scrap、Rework。

必须支持：

- FIFO、优先级、最短队列、轮询、加权路由；
- 有限/无限缓冲、阻塞、饥饿、批处理、拆批、换型、返工和报废；
- 多车任务队列、路段预约、时间窗、避让、充电、装卸和死锁恢复；
- 预热、重复实验、共同随机数、置信区间和确定性回放；
- 吞吐、WIP、Lead/Cycle/Takt、队列、利用率、瓶颈、质量、能耗、成本和订单准交率。

### 5.2 PS：机器人与工位验证

必须支持：

- 机器人关节、工具、基座、用户坐标系和负载；
- 轨迹示教、关键帧、姿态约束、可达性和奇异位姿检测；
- 连续碰撞、最小间距、禁入区、夹具/工装/产品干涉；
- 多机器人同步、互锁、节拍、等待、资源占用和安全逻辑；
- 人员工效、可视性、可操作性和安装维护空间；
- 少量品牌的 OLP profile、程序差异和校准误差报告。

### 5.3 虚拟调试：控制与时序

首批采用开放协议和确定性适配器：

- OPC UA、虚拟 IO、事件总线和回放协议；
- PLC/机器人控制器信号映射、状态机、互锁和安全回路；
- 单步、断点、强制信号、故障注入、超时和时序差异；
- 控制逻辑、物流事件、机器人动作和报警统一时间线；
- 所有输入、输出、版本和故障注入写入 Study 证据。

### 5.4 决策仿真：实验与优化

- 全因子、部分因子、拉丁超立方、随机搜索和参数扫描；
- 敏感性、响应面、约束优化、遗传算法和贝叶斯优化；
- 方案基线、共同随机数、统计显著性、置信带和回归检测；
- 优化目标可组合：吞吐、成本、能耗、WIP、准交率、风险和节拍；
- 优化结果必须保留候选参数、约束、随机种子和原始实验结果。

## 6. 交互体验方案

### 6.1 单工作台布局

```text
左侧：项目/场景/产品/工艺/仿真树
中间：3D 场景、机器人、物流、状态和覆盖层
右侧：上下文检查器（基础 / 仿真 / 控制 / 验证 / 数据）
底部：统一时间线（仿真、机器人、PLC、报警、遥测）
顶部：保存、运行、实验、验证、发布、撤销/重做
```

不要求用户在编辑器、运营页、机器人页之间来回复制数据。`/operations` 保留为深度证据和跨 Study 分析工作台，编辑器负责建模、运行和快速反馈。

### 6.2 两条入口

**快速通道**：拖入预制体 → 自动出现合法默认参数 → 点两个对象建立连接 → 点击运行 → 直接看到吞吐、瓶颈和告警。

**专家通道**：进入高级检查器，配置分布、班次、故障、资源池、控制器、实验矩阵、优化目标和统计口径。

两条通道写入同一个模型，快速通道不能生成另一种简化数据。

### 6.3 关键交互原则

- 每个对象同时显示几何、工艺角色、仿真参数、控制信号和数据绑定。
- 所有仿真参数使用单位、范围、默认值、来源和影响说明。
- 运行前显示模型检查结果：错误、警告、可忽略项和修复动作。
- 运行中提供进度、事件速度、取消、资源预算和日志；不允许无反馈等待。
- 结果直接定位到 3D 对象、队列、机器人、信号或工序。
- 每个图表可追溯到输入版本、Study、重复次数和统计口径。
- 任何 AI 生成的建模变更先显示差异，用户确认后提交，支持撤销。

### 6.4 视觉与动效

遵循 `design-taste-digitaltwin`：工业状态采用颜色、图标、文字三重编码；场景使用雾、地面网格渐隐、PBR、ACES 和克制 Bloom；告警采用呼吸灯和扩散环；仿真播放采用统一时间线和可暂停回放。所有面板支持深浅主题、响应式布局、键盘操作和 reduced-motion。

## 7. 交付路线

### R0：合同和证据底座（4–6 周）

- 冻结统一领域模型、时间协议、坐标帧、单位和 Study 版本；
- 把 Plant Lite、场景绑定、Study 和 Worker 统一到一条 API；
- 建立 10 个黄金样例：单线、多品种、故障、换型、多 AGV、死锁、机器人碰撞、PLC 互锁、变更传播、报告复现；
- 建立性能、确定性、断点恢复、取消和权限门禁。

退出条件：同一输入和 seed 在浏览器、桌面、服务端生成一致结果；失败不污染旧版本。

### R1：Plant 替代版（8–12 周）

- 完整物流对象库第一批；
- 多 AGV 调度、路段预约、死锁与跨域交接；
- 实验矩阵、置信区间、瓶颈/队列/能耗/成本分析；
- 3D 路径、热力、KPI、Gantt、Sankey 和 Study 报告；
- 服务端批量实验和结果缓存。

退出条件：真实中型生产线可完成建模、运行、实验、对比、回放和报告发布。

### R2：PS 工位与虚拟调试（12–16 周）

- 机器人运动学、碰撞、可达性、节拍和多机器人同步；
- OPC UA、虚拟 IO、控制信号、故障注入和时序断点；
- 工位安装、维护空间、人员安全和验证报告；
- 首批机器人 OLP profile。

退出条件：真实工作站可完成轨迹示教、碰撞验证、节拍验证、信号联调和证据回放。

### R3：PD/PPR 与数字线程（12–16 周）

- EBOM/MBOM/BOP/BOE 统一关联；
- 工序、资源、工时、线平衡、作业指导书；
- 配置/变型、变更传播、影响分析、审批和基线；
- 从设计变更到仿真回归、报告和发布的完整链路。

退出条件：设计变更可自动定位受影响工序、资源、场景对象、仿真结果和作业指导书。

### R4：行业库和生态（持续）

- 汽车、电子、离散装配、仓储物流等行业模板；
- 格式 profile、机器人品牌、PLC 适配器和插件 SDK；
- 团队协作、模型差异、Git/版本库和离线部署；
- AI 建模、结果解释、异常诊断和优化建议。

## 8. 验收门槛

### 正确性

- 过程仿真结果与参考模型在冻结容差内一致；
- 相同模型、输入、版本和 seed 可复现；
- 机器人碰撞、可达性、节拍和控制时序有黄金样例；
- EBOM/MBOM/BOP/BOE 变更关系可追溯。

### 性能

- 正式仿真不依赖渲染帧率；
- 长任务可取消、可恢复、可观测；
- 交互反馈 100ms 内可见；
- 中型工厂场景保持稳定帧率，大型场景使用 LOD、实例化、分块和预算调度；
- 报告生成、批量实验和结果查询有 P95 指标。

### 用户体验

- 新用户 30 分钟内完成一条简单生产线仿真；
- 专家用户无需离开工作台完成完整高级配置；
- 每个错误都有定位、原因和修复动作；
- 结果可以从 KPI 一键定位到场景、对象、事件和输入；
- 重要流程通过深色/浅色、1440/980/480 宽度和键盘操作验收。

### 交付证据

- 每个功能都有真实样例、失败样例、输入哈希、输出哈希和版本；
- 格式导入区分 inspect、preview、visual-complete、engineering-verified；
- 报告包含模型版本、参数、随机设置、统计方法、限制和校准证据；
- 发布包可在断网干净 Windows 环境启动、运行、回放和导出。

## 9. 组织与资源建议

至少按四个长期小组组织，而不是按页面拆人：

1. **数字线程与 PPR**：产品、工艺、资源、变更、权限、发布。
2. **Plant 仿真**：DES、物流、实验、优化、统计和性能。
3. **PS/控制**：机器人、碰撞、物理、PLC、虚拟调试和 OLP。
4. **体验与验证**：工作台交互、场景覆盖层、报告、可用性、真实产线 QA。

每个小组必须共享合同、黄金样例和 Study 证据，不能各自维护“看起来能跑”的演示分支。

## 10. 最终产品定义

达到“完全平替”的标准不是功能名称相似，而是客户能用同一个项目完成：

```text
导入产品/工厂数据
→ 建立 MBOM/BOP/资源
→ 放置并绑定 3D 工位与物流
→ 配置班次、故障、控制和机器人
→ 运行仿真与实验优化
→ 发现瓶颈、碰撞、节拍和控制问题
→ 生成报告与作业指导书
→ 变更后自动回归并发布基线
```

这条链全部通过真实样例、可复现结果、失败恢复和用户体验验收后，才能对外宣称 PS/PD/Plant 替代能力。
