## 0. 一句话结论

三端无感的关键**不是"让同一份代码在三端跑"**(那必然滑向 WebView 或 WASM),
而是**"让同一份 IR(指令)在三端被各自的原生 runtime 解释"**。

"好前端生态 + 极致性能"的统一公式是 **分层 + 编译期固化**:
前端生态只留在编辑器一侧;发布产物里没有 React、没有 DOM、没有虚拟 DOM,只有数据与指令。

本项目已有的 deep-engine TS/Rust 双实现、deep2d painter、runtimePackage 概念、golden 契约,
已经站在正确路线上 —— 缺的是 **发布包定型 → 编译期烘焙 → 跨端门禁** 三步。

## 2. 为什么"共享 WASM 内核 + WebView 承载 DOM"(GPT 方案)不够

先分清它对的部分,再驳它不需要的部分:

**保留**:IR 中心、渲染器抽象(Renderer 接口)、状态机替代脚本、GPU 层与 DOM 层各有分工。

**不需要**:

1. **共享 WASM 内核**:本项目 web 端已是 TS + WebGPU 直连,原生端已是 Rust + wgpu。
   中间再塞一层 WASM 内核 = 引入第三份实现 + 一份胶水 + 一份跨端 ABI 维护成本。
   跨端一致性应该用 **"契约 + 代码生成 + golden 门禁"** 保证,而不是"共享二进制"——
   项目已经这么做了(golden fixtures 就是证据)。
2. **WebView 承载富文本 / ECharts / 视频**:这个方案隐含的前提是
   "发布端要在原生里复现 web 的一切"。但发布产物里**根本不该有编辑器外壳**。
   正确的切割是**把范围切掉,而不是把 DOM 搬过去**:内容里的图表在发布时已经固化成
   deep2d 指令,原生端不需要再跑一次 ECharts。
3. 它的分阶段(第一阶段 Web 闭环 → 第二阶段 WASM 核心 → 第三阶段原生后端)把顺序做反了:
   对本项目,第三阶段的产物(原生 GPU 后端)**已经存在**,真正的缺口是"发布包定型 +
   编译期烘焙"。

一句话:**它的方案是"让原生端追上 web";正确的方案是"让两端都退到 IR 之后"。**

## 3. 五个点名技术的体检

### 3.1 Dioxus(Rust,React-like)

- **机制**:`rsx!` 宏(编译期把声明式视图变成 Rust 代码)+ signal 状态 + renderer trait 抽象;
  desktop 走 wry(WebView),web 走 WASM,移动同理。
- **判定**:触了你两条禁忌(WebView、WASM),不能作为整体方案。
- **抄什么**:`rsx!` 的"声明宏 → 编译期代码生成"思路(正是我们要的编译期固化);
  以及它的 renderer trait 抽象 —— 与本项目 `deep2dDisplayList` 合同是同一件事的不同层次。
- **不抄**:它的多端落地方式(wry/wasm)。

### 3.2 egui(立即模式)

- **机制**:每帧从状态重建 UI → 生成绘制图元 → 提交给 wgpu/glow。**本来就没有虚拟 DOM、
  没有保留树**,所以运行时极薄;web 端走 WASM。
- **判定**:它证明了"**每帧从状态生成绘制指令流**"在性能上完全可行 —— 这正是 deep2d 的哲学。
  但 UI 生态、富文本、复杂布局是它的短板,不适合做编辑器外壳。
- **抄什么**:立即模式 / 指令流的心智模型;"单一 wgpu 后端覆盖桌面 + 移动"的工程路径。
- **不抄**:把面板类 UI 也做成立即模式。

### 3.3 GPUI(Zed 的 UI 框架)

- **机制**:retained 元素树 + CSS-like 样式系统 + GPU 自绘 + 自研文本系统;
  为"高帧率专业编辑器"而生,**完全不用 WebView**。
- **判定**:是本项目 deep2d / deep-engine 雄心的**最接近样板**;
  但它以桌面为先(macOS 起家)、**没有 web 端答案**、第三方复用门槛高(文档/API 不稳定)。
- **抄什么**:元素树与样式的模型划分;原生文本与 IME 的桥接做法;GPU 管线的性能纪律
  (它敢把整窗交给 GPU 画,且做到了发布可用)。
- **不抄**:期望它同时解决 web 端 —— 它解决不了。

### 3.4 声明式 DSL 路线(Slint / QML / SwiftUI / Compose / Satori)

> 你说的 "dsl" 我按"声明语言 + 编译期 + 多渲染后端"这一类解读;若指某个具体项目,我再补。

- **Slint**:`.slint` 编译到 Rust/C++/JS,渲染后端覆盖 软件渲染 / wgpu / Direct2D / Metal;
  web 目标仍靠 WASM(所以 web 端不能照抄)。
- **QML**:场景图 + 各平台 RHI,"一份声明多后端"最成熟的先例,但生态老化、许可复杂。
- **SwiftUI / Compose**:声明式 → **平台原生控件**渲染,一致性依赖平台(跨端画面不一致),
  与"三端一致"目标冲突,只作架构参考。
- **Satori(`vercel/satori`,web 生态)**:构建期把 HTML/CSS 渲染成 SVG ——
  **"编译期固化"在 web 生态的最强先例**,值得直接抄它最关键的取舍:
  **只支持受控子集**(CSS 子集 + flex 布局),不支持的一律拒绝。
- **抄什么**:"受控子集"的克制(这决定了多端一致性的上限)+ "声明 → 编译 → 多后端"的分层。
- **不抄**:为发布产物再造一门用户可见的 DSL —— 我们用户侧的表达已经是编辑器里的可视化数据。

### 3.5 uni-app x 蒸汽模式(Vapor)

官方文档要点(已抓取 `doc.dcloud.net.cn/uni-app-x/app-vapor.html`):

- 对比对象是 uni-app x **自己的 VDOM 模式**:VDOM 模式会先建 VNode Tree 再建真实 DOM,
  加载慢、运行有开销。
- 蒸汽模式:**去掉虚拟 DOM**,`template`/`style` **直接编译为底层 C 代码对应的机器码/字节码**;
  官方目标说法是"基于原生渲染管线、渲染性能超过原生 UI 框架"。
- 架构上**仍保留"逻辑层 / 视图层分离"**(逻辑层 script 用 uts/js);**仅支持组合式 API(setup)**。
- **判定**:它验证了本分析的核心命题 —— **性能来自"把 diff / 解释搬到编译期"**,
  而不是"运行时换个更快的 VM"。同时它也承认:即便能力如 DCloud,分层仍然必要,
  只是把跨层代价从运行时(setData 通信)挪到了编译期(生成的同步调用)。
- **抄什么**:发布期做"编译"、运行时只做"执行";为性能接受**能力子集化**的代价。
- **不抄**:UTS 自造语言 + 平台原生控件渲染(与自绘一致性目标不同路)。

### 3.6 小结表

| 技术 | 一致性机制 | web 端靠什么 | 对本项目的结论 |
|---|---|---|---|
| Dioxus | 同一份 Rust 代码多端编译 | WASM | 只抄 rsx 宏与 renderer 抽象 |
| egui | 立即模式指令流 | WASM | 证明"指令流"路线可行;只适用工具型 UI |
| GPUI | 自绘 + 元素树 | 无答案 | 架构样板;抄元素树/样式/文本/IME |
| DSL(Slint 等) | 声明 → 编译 → 多后端 | WASM | 抄"受控子集 + 编译期固化" |
| uni-app-x 蒸汽模式 | 编译期去掉 VDOM | 原生控件 | **抄"发布=编译"的范式**;不抄其语言与控件路线 |

## 4. 目标架构:三层 + 一个编译期

```
┌─────────────────────────────────────────────────────────────┐
│ L1 声明层(只存在于编辑器 / 构建期,不进入发布产物)          │
│    React 19 + npm 生态 + Three.js 预览                       │
│    职责:开发效率最大化;发布时被"烘焙"掉                      │
└──────────────────────────┬──────────────────────────────────┘
                           │  发布 = 编译(bake)
                           ▼
─────────────────────────────────────────────────────────────┐
│ L2 IR 层(唯一真相 = Runtime Package)                        │
│    场景树 · deep2d display list · 已固化布局 · 行为图         │
│    资产清单与引用 · 能力标注(降级决策结果)                    │
│    平台中立 / 可序列化 / 可 diff / 可版本化                    │
└───────────┬─────────────────────────────┬───────────────────┘
            │                             │
            ▼                             ▼
┌───────────────────────────┐  ┌──────────────────────────────┐
│ L3a Web/WebView Runtime   │  │ L3b Native Runtime           │
│  TS: deep-engine(WebGPU) │  │  Rust: deep-engine-native     │
│  + deep2d display list    │  │  (wgpu)+ deep2d Rust painter │
│  WebView = 同一份产物+宿主桥│  │  同一 IR,不同解释器            │
└───────────────────────────┘  ──────────────────────────────
                    │                        │
                    └──── golden 逐像素门禁 ──┘
                        (CI:同包三端比对)
```

**编译期(发布动作)要烘焙的清单**:

1. 布局预计算(在构建期算完,IR 里只存结果,运行时不做布局)
2. 样式固化(继承/级联/变量全部展开)
3. 字体子集化 + 嵌入
4. 纹理/图集预编码(含压缩纹理格式选择)
5. ECharts 等生态组件 → deep2d 指令(发布时一次性转换)
6. 脚本 → 行为图 / 字节码(优先行为图,见 5.3)
7. 能力降级决策(用 support matrix 在发布时算好,写进 IR)

**范围切割(最重要的一条)**:

- 发布产物**不含**编辑器外壳、npm 依赖、ECharts 运行时。
- 原生端需要的是 **Viewer/Player**(`deep-engine-native` 的定位已经对),不是第二个编辑器。
- "webview" 目标 = L3a 产物 + 宿主桥,**不需要第三套 runtime**。

## 5. 边界与硬骨头(按风险排序)

1. **文本(最高风险)**:跨端一致最硬处。方案:发布期把"排版结果"烘进 IR
   (shaping / 断行 / 字体回退在构建期完成),运行时只做字形栅格化与缓存。
   工具:Rust 侧 `cosmic-text` / `rustybuzz` / `fontations`;这样 TS 端不必复刻 shaping。
2. **输入法 / 表单**:发布产物中的输入**不要自绘** —— 用隐藏原生控件 + IME 桥
   (Figma / Chrome 的通行做法:隐藏 textarea 承接 IME,文本显示由自绘层负责)。
3. **行为层**:优先"行为图 / 状态机"(类似 Rive 的状态机 + 数据绑定),而不是脚本 VM。
   真要脚本时再上沙箱(QuickJS 系),且只暴露白名单 API。理由:VM 是跨端一致性的成本黑洞。
4. **一致性机制**:一份 spec → 生成 TS + Rust 常量(代码生成防漂移)+ golden 逐像素回归进 CI。
   **不共享二进制**;着色器层交给 `naga`(WGSL → 各后端)保证单一定义。
5. **性能预算**:每帧热路径 = IR 遍历 + GPU 提交。禁止热路径出现 JSON 解析、正则、字符串拼接;
   IR 用紧凑二进制或 TypedArray 友好布局。
6. **能力降级**:发布时决策,运行时不再探测;降级结果可回显给用户(减少"为什么这里不一样"的困惑)。

## 7. 分阶段落地

| 阶段 | 内容 | 成本 | 收益 |
|---|---|---|---|
| **0** | 发布产物定型为 Runtime Package(离线包导出;web 端做 runtime 加载器) | 低 | 三端一致有了"唯一真相" |
| **1** | web 端编译期烘焙(布局/样式/ECharts 指令化;外壳仍是 React) | 中 | 发布产物脱 DOM,性能上台阶 |
| **2** | 原生 runtime 扩平台(wgpu → mac/linux;移动 + 平台输入桥) | 中高 | 原生目标覆盖 |
| **3** | 跨端门禁:golden 逐像素回归进 CI;support matrix 驱动降级 | 中 | 一致性可验证、可回归 |
| **4** | (可选,高风险)编辑器外壳原生化:Blitz 类渲染 or React reconciler → deep2d | 高 | 原生端也能编辑 |

**建议**:0 → 1 → 3 先行(web 闭环 + 门禁),阶段 2 与业务需求挂钩,阶段 4 在阶段 0-3 稳定前不投入。
