# 全量差距分析:完成当前任务后 vs Unity / UE5 / Three.js / Babylon(2026-09-19 深夜)

前提:本分析以"今晚已落地 30 commit + 在途车道(R6-2 细分埋点、E02-IES 着色注入)完成"为基线,以五轴定档(超越 Babylon/Three、对标 Unity)为口径。**每条缺口给:现状证据 → 差距 → 建议 → 归属任务**。分级:🔴 差距大(数量级)、🟡 有差距(可追平)、🟢 已领先或持平。

## 一、性能劣势(按今晚实测)

### 🔴 P-1 多线程 CPU 提交:Unity/UE 有 Job System,我们单线程
- **证据**:今晚基线 cpu-submit 3.35ms / 帧间隔 5.37ms = **62%**,单线程编码;Unity DOTS Job System + Burst、UE TaskGraph 十几年优化,万级 draw 的 CPU 帧时间可压到我们 1/3 以下。
- **建议**:C2 并行 encoder 农场(widget 级并行 encode、主线程按序 submit)是第一刀(3–5 天);配合 R6-1 热点档(wgpu 队列串行化补丁)。**接受现实**:wgpu 内部有序化(#5525)决定了多线程收益有上限,必要时 wgpu-hal 直下。
- **归属**:R6-2-C2、R6-1 热点档。

### 🔴 P-2 无遮挡剔除的生产化 GPU 管线(UE Nanite/两阶段剔除)
- **证据**:R4 已把 HiZ 全链 DCIR 化(26–32% 快于手写)+ 三端逐位认证,但**仅深度缩减内核**;完整两阶段(HiZ 遮挡判定→可见性缓冲→间接绘制)无 compute 消费点,DCIR v0 无 buffer I/O。UE Nanite 是全 GPU 驱动管线;我们 instancing 有但 draw 全部 CPU 提交。
- **建议**:DCIR v1(buffer read/write、storage 纹理)是前置,然后 HiZ 遮挡判定 kernel → 间接 draw。这是把 cpu-submit 3.35ms 里"5000 实例逐实例编码"打掉的根路径。
- **归属**:R2 v1 → R4(已批 G2)。

### 🔴 P-3 几何处理系统:mesh shader / Nanite 级虚拟几何 / LOD 链自动化
- **证据**:meshlet 有研究路径(D06),无自动 LOD 链、无 impostor、无编译期 HLOD(已批 G3 未实施)。UE Nanite 级虚拟几何 = 数年工程,我们诚实不追全量。
- **建议**:编译期路线(我们独有的形态):编译器产 HLOD/impostor/meshlet 预分区(G3),运行时零成本。放弃与 Nanite 比运行时虚拟几何,比"编译到骨头"。
- **归属**:G3 + R8(首帧可交互)。

### 🟡 P-4 着色编译管线:PSO 缓存/管线预热
- **证据**:有 pipelineWarmup(QA 夹具里有统计);Unity 有 PSO 缓存跨启动、UE 有 PSO 预编译+ Driver Cache。
- **建议**:磁盘 PSO 缓存(wgpu 有 shim API)进编译包;首帧卡顿直接进 R8 冷启动账本。
- **归属**:R8 + B05。

### 🟡 P-5 内存/流送:无虚拟内存/streaming 预算系统
- **证据**:有驻留控制器、上传预算(B05);UE 有完整的流送代理/IO 分块异步、Unity 有 Addressables。我们的流送是"包整载",大场景首帧吃亏。
- **建议**:编译期按分区打包 + 运行时分区流送(与 D05 语义分区合流);优先级由相机轨迹前瞻(C4 已在 R6-2 清单)驱动。
- **归属**:D05 + R6-2-C4。

### 🟢 已领先(保持)
- **确定性**:三端逐字节(R2 认证 12 案例/46 级 + R3 状态合同 + ② 动态重放)——四平台无一具备。
- **编译链**:source map/增量构建/原子回滚/版本冻结——四平台无产品化对位。
- **GPU 时间戳微基准方法论**:三端同口径校准。

## 二、效果劣势

### 🔴 E-1 实时 GI 深度:Unity 7 Surface Cache / UE Lumen
- **证据**:探针 clipmap + r14 跨端阈值通过(⑤),但**动态物体间接光、室内外漏光、表面缓存级更新**未达;Unity 7/UE Lumen 的 GI 是"动态全场景"级,我们是"探针卡距"级。
- **建议**:R1 分两步:先补动态更新+复杂几何(超越线全绿——Babylon/Three 无 GI),再表面缓存对位 Unity(对标线)。明确接受"Lumen 级动态 GI 在浏览器端无人做到"的事实,以三端同语义为差异化。
- **归属**:R1 + E03(已排,GI 车道)。

### 🔴 E-2 体积与大气
- **证据**:exp2 高度雾只有;UE 体积雾(VFT)、Nanite 雪地/植被交互是标配级;Babylon 9 volumetric 增强。
- **建议**:G7 光线步进参与介质(已批),与 E05 灯光联动;范围先做"单体积雾 + God rays"不追全天气系统。
- **归属**:G7(已批未排期——**建议提为 Wave 2 首位**,工业氛围感差距最直观)。

### 🔴 E-3 材质模型深度
- **证据**:PBR + 清漆/玻璃语义(C02)在验收中;UE Substrate/Unity StackLit 的分层材质、全新光照模型覆盖(hair/foliage/water)我们无计划——**接受不追**,工业场景优先级低。
- **建议**:维持"高频字段优先"(C04/C05),把分层材质列为远期观察;水面/车漆两个工业高频项单独评估。
- **归属**:C04/C05 已有卡。

### 🟡 E-4 后处理栈完整度
- **证据**:Bloom/ToneMapping/GTAO/雾有;UE 的 SSR 高质量回退链、运动模糊、DoF、自动曝光我们缺项或质量档浅。
- **建议**:SSR(含离屏回退)是 E04 在办;运动模糊/DoF 按工业场景真实需求排,不追游戏全栈。
- **归属**:E04。

### 🟡 E-5 阴影深水区(在途)
- **证据**:CSM/局部阴影/接触阴影在 E05 验收分母;PCSS 可变软阴影、RT 阴影无。
- **建议**:E05 逐格补(PCSS 进分母);RT 阴影走 R6-1 compute 模拟档,不追硬件 ray query 分母。
- **归属**:E05 + R6-1。

### 🟢 已领先
- IES 光域网:量化表+双端 golden 已落地,着色注入在途——Babylon/Three 无内置体系。
- 双端确定性视觉:同输入同像素是工业验收的硬价值。

### 叠加后的三个新结论

1. **Unity 7 无破坏性迁移 → G6 政策修正**:原"2027Q1 后做 URP/HDRP→统一管线迁移对拍"降级为"重测 GI/光照数字即可",迁移成本红利比预想小;但 Surface Cache GI 抬高了对标线,**R1 的紧迫性上升而非下降**。
2. **Web 层 compute 的超越窗口 = 2026Q4–2027Q1**(Babylon 10 发布前):R4/A2 的数字必须在这个窗口拿到,否则超越只能靠确定性维度单独支撑。Wave 2 排序从"按依赖"改为"按窗口":**R4 万灯 + A2 几何 compute 化是时间敏感任务**。
3. **AI 轴成为下一版本周期的基本盘**:R5 从远期提前,且我们的形态(可校验、可回滚、可审计的 AI 事务)恰好是工业客户在 AI 时代唯一敢买的形态——这是把差距翻成对位优势的最大机会。

## 六、2026-09-19 用户指示:可追项升级(物理/动画/Nanite/Lumen + 调试器核实)

用户四条指示:效果与性能缺口纳入后续任务;Nanite/Lumen 能追则追且求超越方案;物理/动画可追(有成熟方案);核实帧调试/性能分析器在 Three/Babylon 生态的现状。核实结果与立卡如下。

### 6.1 Nanite:从不追改为"开源肩膀上的追"(升级)

- **新情报**:Bevy 0.14 已有开源 Nanite 级虚拟几何(jms55:visibility buffer + 软件光栅化小三角形 + GPU-driven LOD/剔除,代码上游);2026 年 CuRast 论文(CUDA 软件光栅化十亿三角形,宣称 2–5× 于硬件管线,Nanite 自家软 raster ≈3×);NVIDIA 2025 开源了连续 LOD cluster 层级工作。
- **对位方案(超越路径)**:以 Bevy virtual geometry 的可见性缓冲架构为参考(合法借鉴架构,自研实现),把"软件光栅化小三角形"作为 DCIR v1 的第一个重量级 compute 负载——我们独有的**三端逐位确定性**恰好解决软 raster 的跨 GPU 数值分歧问题(这是 Bevy/NVIDIA 都没有的验证基建)。编译期侧与 G3(HLOD/meshlet 预分区)合流。
- **立卡 R9(虚拟几何)**:阶段一 visibility buffer + meshlet 预分区(依赖 G3);阶段二 DCIR v1 软件光栅化 kernel + 逐位验证;阶段三 GPU-driven LOD 层级流送。量级:大(季度级),但每一阶段独立可用。

### 6.2 Lumen:追,方案 = DDGI 探针体 + 编译期(升级)

- **新情报**:Lumen 的核心思想 = 软件光追 + 表面缓存 + 距离场;开源对位 = **DDGI**(Dynamic Diffuse GI,Majercik 2019,探针体+无限滚动网格,Godot/Bevy/Falcor 均有实现先例)。
- **对位方案**:R1 的表面缓存阶段直接采用 **DDGI 架构**(探针体已有——我们的 probeClipmap 就是探针网格,补:射线追击(距离场+软件光追)、探针无限滚动、无限更新+验证启发式)。超越路径同样走确定性:探针更新 kernel 进 DCIR,**跨端逐位一致的实时 GI 全行业没有第二家**。Lumen 的距离场依赖编译期 mesh SDF——这又是编译链优势(编译器产 SDF,运行时零成本)。
- **归属**:R1 阶段二(表面缓存)改写为 DDGI 架构;编译期 mesh SDF 产线归 G3/编译链。

### 6.3 物理:Rapier/Avian 路线确认

- **新情报**:Rapier(dimforge,纯 Rust 2D/3D,成熟稳定)与 Avian(bevy_xpbd 后继,ECS 架构,当前 Bevy 生态最活跃)是两条现成路线;Rapier 有 WASM 版 → **Web 与 Native 同一物理内核可行**。
- **立卡 R10(物理)**:F04/F05(宿主接线/机械约束)继续;物理内核选型 Rapier(双端 WASM+native 同源,确定性可验证——fixed timestep 下 Rapier 是确定性的,正好接我们的逐位门禁)。超越点:**跨端确定性物理重放**又是独家形态。量级:中。

### 6.4 动画:不引引擎,按工业范围自补

- **新情报**:成熟组合 = 引擎内建动画 + Bevy Animation Graph(动画图/状态机);retargeting 在开源世界也是短板(Bevy 0.17 仅基础支持)。工业场景以机械动画(TRS/路径/约束驱动)为主,角色动画非重点。
- **立卡 R11(动画)**:F01 正式动画包基础上补:动画状态机(有限状态+过渡条件,进 R3 确定性合同)、路径/约束驱动动画(工业机械臂正路)、关键帧曲线编辑(编辑器已有基础)。retargeting 不做(如实)。量级:中小。

### 6.5 帧调试器/性能分析器:生态核实结果与我方定位

## 七、与 Bevy 的性能对比 + Godot/Falcor 可借鉴点(2026-09-19 深夜,深度核实)

### 7.1 我们 vs Bevy:性能对比(诚实版)

**关键事实:Bevy 的渲染后端就是 wgpu**——"Bevy vs 我们"不是 API 之争,是"通用引擎调度开销 vs 专用编译链"之争。逐层对比:

| 层 | Bevy | 我们 | 判定 |
|---|---|---|---|
| GPU 抽象 | wgpu(同款) | wgpu(同款) | 平手 |
| 渲染提交 | 通用 ECS 抽取→渲染世界(每帧全量同步);调度器并行有官方承认的开销 | 编译期产 RenderPacket(静态部分零运行时决策);运行时按变更集增量 | **我们占优**(内容已知形态) |
| Draw 数 | 虚拟几何后=少数 indirect draw(0.15 起 per-cluster 实例化) | 当前 5000 实例逐 draw;虚拟几何未建 | **Bevy 占优**(这是 R9 要追的) |
| ECS/CPU 场景管理 | world 类内建,通用调度,官方承认调度开销高于预期 | 无通用 ECS;编译链直出场景,B02 脏域增量 | 场景已知时我们占优;动态任意场景 Bevy 占优 |
| 阴影/GI/后处理 | Bevy 逐步建设(实验性);无实时 GI 生产 | cluster/CSM/探针 clipmap/烘焙 GI 均有真实证据 | **我们占优**(工业渲染纵深) |
| 确定性 | 无 | 三端逐位门禁 | **我们独占** |
| 生态/迭代速度 | Rust 社区活跃,月度发版 | 专用产品团队 | Bevy 占优 |

**结论**:纯渲染管线(虚拟几何)Bevy 今天领先(R9 追);场景已知、重光照/诊断/交付语义的工业负载**我们结构性强于 Bevy**——因为 Bevy 必须为"任意游戏"设计通用性,我们只为"编译过的工业世界"设计。这不是自夸:Bevy 的 ECS 通用性买不来编译链,我们的编译链也买不来 Bevy 的任意场景能力——**赛道不同,但在我们的赛道(Bevy 也想进的 digital twin/工业可视化)我们有结构性优势**。

### 7.2 Bevy 可借鉴(具体到模块)

4. **教训同样值钱**:官方承认"调度并行开销高于预期"、"meshlet 简化是瓶颈"、"低模用虚拟几何反而亏"——我们 R9 必须带场景门槛判定(低模走常规管线)。

1. **RenderGraph 组合式 pass 框架**:研究代码与后端样板隔离——我们 B03 RenderGraph 的"计划↔执行"对拍语义可参考其图编译/自动 barrier 处理;

## 八、DAG 的用处与我们的现状(2026-09-19 用户追问,本地代码审计)

**结论:DAG 有用,而且我们已经在用——真正的缺口不是"没有 DAG",而是"DAG 编译结果没被榨干"。**

### 8.1 DAG 在渲染里的三种形态与我们的覆盖

| 形态 | Falcor/Slang 的用法 | 我们 | 判定 |
|---|---|---|---|
| **Pass 级 Render Graph**(Falcor RenderGraph) | 声明式 pass 图→编译期拓扑排序、死 pass 剔除、资源生存期分析→**内存别名复用**、自动屏障 | `renderGraph.ts` 已有:topologicalOrder+环检测、`aliasKey` 槽位按生存期复用(lastUse<first 即复用)——**核心两项已在** | 有基础,欠榨干 |
| **着色器级 DAG**(Slang 模块图;R2 DCIR) | 模块依赖图、死代码消除、跨后端发射 | DCIR v0 就是 typed 节点 DAG | 已有(R2 持续) |
| **帧计划级 DAG 序列化**(Falcor 没有,B1 独有) | — | 编译期把"这帧画什么"的 DAG 执行序固化成重放脚本(内容哈希键) | **独有机会**,未建 |

### 8.2 没被榨干的三项(升级 B03)

1. **死 pass 剔除**:图编译时把无消费者的 pass 从执行计划剔除(如:无透明物→transparent pass 出局)——直降 CPU 编码时间,正打 62% 痛点;
2. **并行子树检测**:DAG 的独立子图=可并行 encode 的天然单元——**C2 并行 encoder 农场的 job 划分不该按 widget 数拍脑袋,应按 DAG 独立子图切**;
3. **计划序列化**(=另一会话分析的 B1):DAG 拓扑序+编译决策按内容哈希固化,运行时命中即重放——0.25ms 缓存路径覆盖面扩展。

### 8.3 边界(诚实)

- wgpu 内部自带 barrier 跟踪:我们图级调度的价值在**顺序/别名/剔除/并行**四项,不在屏障(Falcor 自己插屏障是因为它直接面对 D3D12/Vulkan);
- Falcor 的研究级灵活性(任意 pass 组合)不照搬:我们的图是"固定工业管线+数据驱动子图",DAG 编译的爆发点在**看板 widget 子图**(每帧内容变化,图随之变——这正是引擎们没有的"内容已知"优势);
- 拓扑序用稳定 tie-break(按声明序)——否则并行/重放会破坏逐位确定性。

**行动 #18(B03 升级,1-2 天)**:renderGraph 编译器补死 pass 剔除+并行子树分析,输出喂给 C2;计划序列化接口预留(接 B1)。全部本地可做,平台配额恢复后立即可开工。

## 十、三轴章程(2026-09-19 用户定调:极致性能 / 优秀效果 / 尽量轻量化)

三轴即 R6/R7/R8 的定位纲领,所有任务卡的取舍以此裁决:

| 轴 | 纲领 | 度量 | 已有抓手 |
|---|---|---|---|
| **极致性能 R6** | 不接受"够用";CPU 准备、GPU 管线、瓶颈段全部进账本,62% 红线事件是样例 | 四段细分+GPU timestamp+六类负载,季度重测 | R6-0/1/2、C2/A/B 组、R4、R9 |
| **优秀效果 R7** | Web 层全面超越 Babylon/Three,Unity 7 Surface Cache GI 为对标线;每格效果证据可复现 | R1 GI/DDGI、G7 体积、E02-IES、E04 SSR、E05 PCSS/接触阴影、C04/C05 材质 | 全部在途或已排 |
| **轻量 R8** | 同能力下安装/包体/内存显著小于 Unity/UE 运行时;web 首屏/首帧领先 | bundle/EXE/wasm/运行包/内存账本+冷启动 | size-ledger 已建,B05 预算,C07 增量 |

**轻量化的第四层含义(本次补强)**:吸收 Bevy/Godot/Falcor 精华时执行**吸收体积纪律**——每项吸收必须报"增量体积/增量依赖/增量内存"三笔账,超过预算即触发重新设计(编译期化或砍范围);禁止"功能进了,体积跟着进"。体积账本(size-ledger)每吸收一项跑一次对比。

三轴冲突时的裁决顺序:**轻量是约束不是目标**——性能与效果在轻量约束内做到极致(例如:能编译期化就不加运行时依赖,能 compute 就不加 CPU 子系统,能复用 DCIR 就不加新着色栈)。
