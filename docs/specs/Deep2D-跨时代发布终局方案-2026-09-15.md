# Deep2D 跨时代发布终局方案

日期：2026-09-15  
定位：在《一源多译·三证无感》和《三端无感发布实现交接》的基础上，给出可落地、可扩展、不会把“支持”说大的终局设计。  
范围：Web、Three WebView、Deep Native；2D、3D、数据、动画、输入、脚本与更新。

## 0. 结论

Deep2D 的终局不是“同一份页面在三端运行”，而是：

> 一份语义源，经增量编译得到一份可证明的运行包；原生核心负责高频确定性路径，兼容计算舱负责长尾生态；两者通过稳定命令与时间轴通信，任一能力都必须在发布前被证明、降级或阻断。

这保留了现有的零 WebView、零 WASM、原生 `wgpu` 主路线，也诚实处理了“完整 ECharts/任意脚本”与“原生端零 JS 运行时”之间不能同时成立的约束。

## 1. 先纠正两个过度承诺

### 1.1 “全部提前烘焙”不成立

布局、字体子集、静态图表几何、着色器和资源索引适合构建期计算；数据刷新、tooltip、筛选、窗口尺寸、IME 组合串、动画时间和网络状态必须保留运行时语义。ECharts 官方 SSR 只适合受限静态输出：SVG 初始动画不能覆盖全部动态效果，轻客户端的数据变化需要再次渲染，不能当作离线交互运行时。[ECharts SSR](https://echarts.apache.org/handbook/en/how-to/cross-platform/server/)

### 1.2 “三证”是验证证据，不是形式化证明

IR hash 能证明输入和中间表示一致，像素对照能发现视觉回归，行为回放能发现状态漂移；它们不能证明任意输入、任意 GPU 驱动或任意脚本的全域等价。因此发布报告必须使用“已验证范围、测试夹具、阈值、已知限制”，禁止写成数学上的全等证明。

## 2. 终局架构：Deep Continuum

```text
编辑器语义源
  ├─ SceneSnapshot / DashboardDocument / ChartSpec
  ├─ BehaviorGraph / ScriptCapabilityContract
  └─ 数据绑定与资源引用
          │ revision + dependency graph
          ▼
增量编译器（Salsa 风格查询缓存）
  ├─ Layout IR（外框布局）
  ├─ Text IR（GlyphRun / InlineBox）
  ├─ Chart IR（标度、数据窗口、交互状态）
  ├─ Display IR（稳定 nodeId、z 序、命中索引）
  ├─ RenderPacket / GPU IR
  └─ Behavior IR（状态机、事件、白名单命令）
          │ target lowering
          ├───────────────┬────────────────┐
          ▼               ▼                ▼
      WebGPU TS       Native wgpu      WebView 兼容面
      参考/发布端      主发布端          独立 surface
          │               │                │
          └─────── epoch / command bus ────┘
                          │
              统一资源、诊断、LKG、回放
```

MLIR 的可取思想是“多层 IR、逐步 lowering、保留高层语义直到真正需要时再消耗”，不是把 Deep2D 改造成 MLIR 工程。[MLIR rationale](https://mlir.llvm.org/docs/Rationale/Rationale/)  增量编译可借鉴 Salsa 的按需查询与缓存模型；它只缓存纯查询结果，不能把带网络副作用的脚本当作纯编译查询。[Salsa](https://github.com/salsa-rs/salsa)

### 2.1 语义源与增量因果图

每个对象都有 `nodeId`、`revision`、`dependencies` 和 `semanticHash`。修改一个数值只重新计算受影响的 dataset window、chart layout、display chunk 和命中索引，不重新解析整包；修改字体只失效受影响的 text runs；修改相机只失效 3D view-dependent pass。

包内同时保存：

- `sourceSemanticHash`：编辑器语义源的身份；
- `compileGraphHash`：各 pass 输入、版本和参数；
- `targetArtifactHash`：目标后端的实际产物；
- `capabilityReport`：对象级 supported/degraded/blocked/webview-only；
- `replayContract`：事件、数据 revision、时钟和随机种子。

### 2.2 Epoch 提交协议

每次更新形成不可变 `Epoch`：`{documentRevision, dataRevision, layoutRevision, resourceSet}`。渲染线程只接受完整 epoch，旧 epoch 继续显示到新 epoch 完成预热并通过校验；数据快照、命中索引、文本布局和画面不得跨 epoch 混用。提交顺序固定为：validate → dependency closure → prewarm → build frame graph → present → commit LKG。

这比“改一个值就热替换几个对象”更安全：它保留增量性能，同时避免图表已是新数据、命中区域还是旧布局的错位。

## 3. 能力分层：原生核心、适配器、兼容舱

| 层 | 内容 | 运行方式 | Deep Native 状态 |
|---|---|---|---|
| N0 原生核心 | 文字、形状、图片、表格、KPI、基础图表、筛选、状态机、3D 联动 | Rust/TS 对同一 IR 的双解释器，统一 epoch | supported |
| N1 原生适配器 | 复杂 SVG、认证过的图表扩展、富文本 inline object、特定动画 | 版本化组件 ABI：输入 schema，输出增量 display list 和命令 | supported/degraded |
| X 兼容计算舱 | 任意 ECharts option/formatter、长尾 JS 脚本、第三方组件 | 独立受限进程或宿主模块；只输出 JSON/二进制命令，不接触 GPU、窗口、文件系统 | 需显式启用；不伪装成 N0 |
| W WebView surface | HTML/CSS、iframe、DOM、浏览器专属 API | 现有 Three WebView 目标 | webview-only；Deep Native 阻断 |

兼容舱是一个产品决策开关，不是偷偷塞进 `runtime/package.json` 的例外。若项目坚持“Deep Native 连 JS 引擎也不能有”，则 X 层关闭，任意 JS 和任意 ECharts 明确为 blocked；不能用截图或 SSR 冒充支持。

## 4. ECharts：最强的诚实路线

### 4.1 默认路线：Chart IR

继续使用已有 `EChartsOptionCompat → ChartIR → Deep2D display list`。Chart IR 只允许已认证的 series、axis、dataset/transform、tooltip、legend、dataZoom、action 和数据窗口；未知字段 fail-closed。图表数据采用列式分块、增量 revision、可解释抽样和预算。

### 4.2 可选路线：ZRender Painter 计算舱

如果产品确实需要复用大量 ECharts 语义，可做一个有边界的实验：在独立 JS 计算舱中保留 ECharts/ZRender 的布局、数据处理和动画，把 Painter 替换为批量命令输出。ZRender 提供 `registerPainter` 与平台接口切口；React Native ECharts 也证明“保留 ECharts 计算、替换 SVG/Skia 绘制出口”可行，但其声明的是大多数图表，不是全量兼容。[ZRender](https://github.com/ecomfe/zrender)，[Wuba React Native ECharts](https://github.com/wuba/react-native-echarts)

计算舱必须满足：

1. 无 DOM、无网络、无任意宿主对象；资源、时钟、随机数和事件由宿主注入；
2. 每帧一次批量提交 `ChartCommandBatch`，禁止逐绘制调用跨边界；
3. tooltip、formatter、图片、扩展、ECharts-GL、HTML rich text 分别认证；
4. 运行日志记录脚本/图表版本、输入 hash、输出 hash、预算和超时；
5. 超时或异常时保留上一 epoch，不能半帧呈现。

这条路线不改变 N0 的纯原生承诺；它提供的是“兼容目标”的强能力，而不是把兼容代码伪装成原生核心。

## 5. 脚本：从“写任意代码”改为“写可证明副作用”

脚本编译为两条路径：

```text
脚本编辑器
  ├─ 纯行为子集 → Behavior IR → TS/Rust 代码生成 → N0
  └─ 任意 JS/依赖 → X 计算舱 → typed CommandBatch
```

N0 子集只允许：数值/字符串/数组的受限操作、状态读取、白名单命令、固定步时钟、受控随机种子。禁止闭包逃逸、动态 import、反射、任意网络、文件、DOM、GPU 句柄和未声明副作用。每个命令带 `invocationId`、目标 `nodeId`、前置 revision 和幂等键。

X 计算舱采用独立进程或明确的 JS 宿主，而非浏览器运行时；进程级内存、CPU、调用深度、消息大小和 wall-clock 预算必须有硬上限。它只能通过 `HostCapabilities` 请求受管能力，返回可序列化值和命令。AssemblyScript 不能作为“TypeScript 无损原生编译器”：其官方状态明确存在动态性、闭包、异常、Promise、JSON 等限制。[AssemblyScript status](https://www.assemblyscript.org/status.html)

脚本验收不是比较任意脚本的最终画面，而是比较：输入事件序列 → 命令序列 → 状态轨迹 → display hash。存在网络或时间副作用的脚本只能在显式 replay fixture 中验证。

## 6. 动态文本、富文本与 IME

文本不能只存截图或 atlas quad。`TextDocument` 保存文本、样式区间、段落、inline object、selection 和稳定 ID；窗口尺寸、数据绑定或字体变化只使受影响段落失效。

- 外框：受限 flex/grid/absolute 与虚拟列表；Taffy 只负责 CSS Block/Flex/Grid 布局，不负责文本 shaping。[Taffy](https://github.com/DioxusLabs/taffy)
- 段内：GlyphRun、字素簇、双向文本、回退字体、断行；Parley 可作为候选，但富文本编辑能力必须单独验收，不能把开放中的编辑器工作当成现成生产能力。[Parley](https://github.com/linebender/parley)
- 绘制：Glyph atlas 增量上传，atlas revision 进入 epoch；缺字形或字体许可失败时对象级 degraded/blocked。
- 编辑：`TextInputSession` 独立维护 composition、selection、caret、撤销事务；IME Preedit 不写入正式文档，Commit 才产生一次编辑命令。验收必须覆盖中文选词、组合期间切焦点、emoji/组合字符删除、RTL、DPI 候选窗定位。[winit IME](https://docs.rs/winit/latest/winit/event/enum.Ime.html)

“无感”只对经过字体和文本矩阵认证的范围成立。任意 HTML/CSS 富文本仍属于 W 或 X，不得因为静态截图接近就标记为原生 supported。

## 7. 三证 2.0：验证矩阵

| 证据 | 比较对象 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 语义证 | source hash、IR hash、依赖图 | 编译输入、版本和对象依赖可追溯 | GPU 像素等价、任意输入行为 |
| 结构证 | display list、命中索引、状态轨迹 | 同一 fixture 的结构和交互结果一致 | 所有字体/GPU/驱动 |
| 视觉证 | 参考光栅化器、WebGPU、Native 截图 | 固定设备/阈值内的画面一致 | 不同驱动全域一致 |
| 资源证 | 每块内容 hash、预算、签名、纯净审计 | 包未篡改、资源闭包和大小可控 | 业务语义正确 |

每个声明都带 `scope`：平台、驱动、字体包、分辨率、时间、fixture、允许差异。发布门禁遇到未覆盖组合只能输出 `unknown/blocked`，不能默认通过。

## 8. 发布协议

容器继续使用 `manifest.json + runtime/package.json`，新增：

```json
{
  "sourceSemanticHash": "…",
  "compileGraphHash": "…",
  "targetArtifacts": [
    {"target":"deep-native","hash":"…","features":["N0","N1"]},
    {"target":"three-webview","hash":"…","features":["W"]}
  ],
  "capabilityReport": {"objects": [], "summary": {}},
  "replayContract": {"clock":"fixed-step","seed":0,"fixtures":[]},
  "updatePolicy": {"atomicEpoch":true,"lkgRequired":true}
}
```

数据连接、凭据、脚本源码和 X 兼容舱包不能混入纯原生 runtime payload；它们分别由 host 配置、签名扩展包和能力报告管理。更新采用内容寻址 delta：下载、校验、预热、present 成功后才提升 LKG；schema 不兼容时保留旧版本并给出可操作诊断。

## 9. 现实的实施顺序

### P0：把当前路线接通

1. D07/D08 直接产出真实 `DeepRuntimePackage`，去掉 `conversionRequired` 假完成状态。
2. Web loader 按 Native 顺序执行 validate → prewarm → atomic commit。
3. 冻结 `DashboardDocument v1`、ChartIR v1、对象级 capability report。
4. 建立 source/compile/target 三种 hash 和首个跨端结构 golden。

### P1：动态核心

1. Epoch 提交协议、依赖图和增量失效；
2. 动态 ChartIR：数据窗口、legend、tooltip、dataZoom、离线 `sim:`；
3. TextDocument、GlyphRun、IME 事务和字体能力矩阵；
4. Behavior IR、命令白名单、固定步回放。

### P2：兼容扩展试验

用一个动态条形图和一个中文富文本输入做淘汰实验：同一事件轨迹、离线数据、动画、tooltip、formatter、IME、异常和超时。若 X 计算舱需要 DOM 仿真、每帧整图重建或无法稳定批量输出，立即停止扩展，回到 N0/N1 能力集；不允许“先兼容再补合同”。

### P3：热同步与平台扩展

对象级 delta、编辑期三端预览、签名扩展包、设备矩阵和发布回滚。新增平台只实现 target lowering、宿主能力适配和同一套验证矩阵；没有三类证据不得称为已接入。

## 10. 淘汰条件与不可妥协项

- 任意对象在报告中标记 supported，但没有对应 fixture 和平台范围：阻断。
- ECharts 通过 SSR 截图声称支持实时交互：阻断。
- 脚本绕过命令总线直接访问 DOM、网络、文件或 GPU：阻断。
- 新增后端把布局、文本 shaping 或 JSON 解析放进每帧热路径：阻断。
- X 兼容舱与 N0 共用可变状态却没有 epoch/revision：阻断。
- 视觉差异未登记能力原因，或故障时呈现半个新包：阻断。

## 11. 最终判断

DeepSeek 两份方案的主轴“发布即编译、语义源、多层 IR、三类证据”是正确的；本方案补上了它们最容易失真的地方：

1. 把静态烘焙改成增量因果编译，保留动态语义；
2. 把 ECharts 和任意脚本拆成原生能力集与隔离兼容舱；
3. 把“三证证明”改成带范围的可审计证据；
4. 把文本、IME、数据 revision、异常和回滚纳入同一 epoch；
5. 把“新平台只需新增 backend”落实为 backend + host adapter + verification matrix。

这条路线的革命性不在于承诺所有东西都原生，而在于让每种能力都能沿着同一条语义、增量、证据和回滚链路演进：高频路径获得引擎级性能，长尾生态保留明确出口，未来新增终端不会再复制整个产品。
