# iTwin Studio 数字孪生 × AI 场景化方案

状态：建议稿  
日期：2026-08-26  
输入：美云智数“美擎数字孪生”应用场景、先导智能《设备预测性维护（PHM）》材料、现有 iTwin Studio 产品与架构规划及当前代码能力

## 1. 结论

iTwin Studio 不应沿着“更逼真的 3D 大屏”继续堆功能，而应升级为：

> 面向工业现场的数字孪生应用创作与智能运营平台。用同一套 BIM/3D、2D 看板、实时数据、视频、仿真和 AI 上下文，把“看见问题”推进到“定位、解释、预测、推演、处置和复盘”。

方案收敛为“一套底座、两个工作面、两条主闭环、两项后续能力”：

- 一套底座：`ApplicationDocument + Data Hub + Binding Runtime + Scene SDK + AI Evidence Protocol`。
- 两个工作面：建设期的应用创作工作台，运行期的运营与处置工作台。
- 两条主闭环：设备异常与预测维护、生产与质量视觉闭环。
- 两项后续能力：资源与物流推演、能耗与排放洞察。
- 一个闭环：感知 → 识别 → 定位 → 分析/预测 → 仿真推演 → 人工确认 → 执行 → 反馈学习。

首期只打通两条可验证闭环：

1. **设备异常与预测维护闭环**：复用 Iot-nb 已有模型资产、在线推理、边缘特征窗口、完整率/漂移门禁、影子评测和模型治理，补齐部件级 3D 定位、知识检索、Case、EAM/CMMS 与复检回流。
2. **生产与质量视觉闭环**：以现有 `VisionCenter + ONNX Runtime` 为唯一视觉底座，补齐产线质量语义、连续帧判定、工位/产品/批次关联、复检标注、QMS/MES 联动和模型评测。

现有 Factory Flow 物流仿真和能耗洞察在双闭环稳定后进入第二阶段；物流不扩张为 APS、MES 或 WMS，能耗不扩张为完整碳核算或自动控制。人才培养、SOP/VR 暂不纳入本轮范围。

## 2. 对参考场景的理解

参考页面给出的五类应用场景是：

| 参考场景 | 实际业务目标 | 需要形成的闭环 |
| --- | --- | --- |
| 设备维护管理 | 故障预测、备件寿命、保养、参数预警 | 设备状态 → 异常证据 → 风险判断 → 处置建议 → 维修反馈 |
| 生产与品质管理 | 声纹、PCB、外观检测，关键因素分析和工艺调优 | 质量事件 → 工位/批次 → 参数关联 → 原因候选 → 复检/调参 |
| 能耗排放与管理 | 能耗预测、设备优化控制、电能质量和预警 | 能源基线 → 偏差识别 → 归因 → 优化建议 → 效果验证 |
| 资源配置协调 | 订单/物料预测、库存、供应协同、路径和排班优化 | 需求/约束 → 方案生成 → 仿真比较 → 人工选择 → 执行回看 |
| 人才培养 | VR 培训、经验复用、缩短培养周期 | 标准作业 → 沉浸演练 → AI 指导 → 评分 → 错误复盘 |

参考产品真正值得学习的不是场景名称，而是三点：

1. 三维只是业务上下文和操作入口，价值来自数据、算法与流程闭环。
2. 预测维护、质量、能耗、物流和培训共用现场模型、设备身份、实时数据与事件体系。
3. 虚实同步、仿真验证和人工处置需要连续，而不是分散在大屏、AI 聊天、视频平台和报表系统里。

### 2.1 预测性维护材料带来的修正

先导智能材料进一步说明，预测性维护不是一个“算出故障概率”的模型功能，而是一条由现场信号和维修业务共同驱动的产品链：

```text
设备/部件/测点建模
→ PLC 与振动、温度等高频采集
→ 边缘清洗、特征提取和本地告警
→ 服务端同类设备对比、模型分析与知识检索
→ 故障预警 → 问题诊断 → 维保方案 → 维保执行 → 维保复检
→ 结果、换件和真实故障回流模型与案例库
```

因此对原方案做四项修正：

1. **对象粒度从设备下沉到可维护单元。** 必须表达设备 → 伺服/电机/气缸/轴承/丝杆等部件 → 传感器/PLC 点位，否则告警只能落到整机，无法指导点检和备件。
2. **加入边云协同。** 高频原始信号在边缘侧完成窗口化、质量检查和特征提取，中心侧保存必要原始片段、特征、告警和结果，避免带宽、时延和存储失控；断网时仍保留本地监测和告警。
3. **闭环覆盖维修业务。** 预测结果必须接入点检、报修、保养、备件和复检，而不止于看板告警；iTwin Studio 负责空间上下文、洞察、协同和证据，EAM/CMMS 继续负责正式工单和库存账。
4. **知识库围绕资产和案例组织。** 手册、调试规范、异常处理文档、故障树、历史工单和工程师结论都必须绑定设备型号、部件、故障码、工况和处置结果，AI 问答只能基于这些可追溯证据回答。

材料中关于准确率、故障覆盖率、停机下降和产值收益的数据均为供应商案例陈述，缺少样本量、口径和对照条件。本方案只将其用作价值假设，不作为产品承诺或试点验收基线。

### 3.2 Iot-nb 的明确复用方案

#### 直接复用

| Iot-nb 现有资产 | 接入方式 | iTwin Studio 中的落点 |
| --- | --- | --- |
| `MaintenanceModelAsset` 与模型制品 | 定义兼容导入器，保留版本、特征、归一化、阈值、指标、数据指纹和生产资格 | `MaintenanceModelPackage` |
| `MaintenanceDeployment` | 复用设备、数据源、特征映射、窗口、采样周期、连续命中、冷却和阈值语义 | `MaintenanceDeploymentPolicy` |
| `loadEdgeFeatureWindow` | 通过 Edge/Data Hub Adapter 读取设备点位窗口，不依赖 Tauri 调用方式 | `FeatureWindowProvider` |
| `executeMaintenanceDeployment` | 抽取本地线性/Ridge 评分、ONNX 推理、输入完整率、分布漂移和贡献特征逻辑 | `MaintenanceInferenceProvider` |
| `evaluateShadowRun` | 复用混淆矩阵、Precision/Recall/F1、千样本误报和提前量，并扩展按设备/故障类型分组 | `MaintenanceEvaluationService` |
| 模型生命周期与推理证据 | 复用候选、验证、发布、退役、批准人、数据指纹和输入窗口留痕 | 模型注册中心与审计记录 |
| Case、工单、反馈字段 | 映射到 `OperationalCase` 和外部 EAM/CMMS 引用 | 处置与复检闭环 |
| 独立 Edge Agent | 作为可选现场运行组件，复用采集、SQLite WAL、可靠队列、保留策略和断网续传 | 边缘节点，不并入 Web 前端进程 |

#### 复用时必须修正

- Iot-nb 当前运行时的 `.9` 完整率、`5σ` 漂移拒绝、至少 30 条样本和影子评测默认门槛不能写死为全行业标准，必须进入模型包和设备部署策略并可审计地版本化。
- Iot-nb 内置涂布、辊压、气缸、化成和能耗模型明确标记为 `benchmarkOnly=true`、`productionEligible=false`，适合样板、合同测试和演示，不得冒充现场生产模型。
- AI4I 公共基准的最佳测试 F1 约为 0.54，且来源是公开合成数据，只用于验证训练评测流程。现场发布必须导入你已有的工厂模型制品，或使用现场数据按设备/批次/时间分组重新验证。
- Python 训练器继续作为离线工具或独立训练服务，支持 Isolation Forest、Random Forest、XGBoost、RUL Ridge、1D-CNN、LSTM、TCN 等制品导出；iTwin Studio 首期只负责模型导入、验证、部署、推理和治理，不复制训练工作台。

### 3.3 延续原规划的边界

- 保持“一个智能洞察入口 + 专业工作台”，不建设独立 AI 门户。
- 使用轻量 `AiCapabilityRegistry` 做确定性路由，不建设自由自治 Agent Mesh。
- 大模型理解意图、组织解释和生成草案；BIM 几何、视觉框、指标计算、预测评分和仿真结果由确定性工具产生。
- 普通问数走受控 `AskDataPlan`，不让模型生成或执行任意 SQL。
- AI 只能产生建议动作或命令草案，不能绕过权限、确认和审计直接发布或控制真实设备。
- 预测维护是独立、可关闭的 `MaintenanceInsightPlugin`，不塞进通用聊天或编辑助手。
- 连接器、视觉模型、预测模型、行业规则和仿真优化器保持插件化；默认安装只带高频、可验证能力。

### 3.4 需要补齐的共性对象

现有规划已有 `StudioAiContext` 和 `InsightEnvelope`，建议增加一个跨场景的运行闭环对象 `OperationalCase`，避免每个场景各做一套告警和工单：

```text
OperationalCase
├── id / type / severity / status / owner
├── applicationId / sceneId / objectRefs[] / locationRef
├── sourceEvents[] / metricRefs[] / evidenceRefs[]
├── hypothesis[] / risk / confidence / dataQuality
├── suggestedActions[]
├── approvedAction / executionRef
└── feedback / outcome / auditTrail
```

`OperationalCase` 不是替代 EAM/MES/QMS 的工单系统。它只负责把孪生现场中的对象、数据、视觉证据、AI 洞察、人工确认和外部系统记录关联起来；正式工单通过连接器推送到企业现有系统。

预测性维护还需要一个轻量资产侧契约，不另建一套资产主数据：

```text
MaintenanceAssetProfile
├── equipmentId / maintainableUnitId / parentUnitId / sceneObjectRef
├── type / model / criticality / failureModes[]
├── signalRefs[]: channelId / source / unit / sampleRate / qualityRule
├── comparableGroup / operatingConditionRefs[]
└── manualRefs[] / sparePartRefs[] / externalAssetRef
```

它引用企业现有资产台账并补充 AI 所需的部件、测点、工况和证据关系；`OperationalCase` 记录一次异常如何被发现、处理和验证。

## 4. 产品方案

### 4.1 产品形态

#### A. 建设期：智能应用创作

面向实施工程师、工艺工程师和数字化团队：

- 导入 BIM/CAD/GLB/IFC，建立设备、工位、空间和摄像头的稳定 ID。
- 接入 MQTT、OPC UA、HTTP、WebSocket、数据库、文件和视频源。
- 通过同一数据抽屉把字段绑定到 KPI、图表、3D 状态、标签、告警和动作。
- 用 AI 根据 Schema 生成看板/绑定/规则/脚本草案，并通过差异预览、局部接受和撤销应用。
- 通过模板安装“设备健康”“质量追溯”“能耗分析”“物流仿真”等场景包。

#### B. 运行期：智能运营与处置

面向生产、设备、质量、能源和管理人员：

- 从总览看板下钻到厂区、车间、产线、工位和设备。
- 告警自动定位到 3D 对象、摄像头画面、趋势窗口、相关批次和责任系统。
- 智能洞察入口回答“发生了什么、影响什么、为什么、接下来做什么”，每条结论可展开证据。
- 高风险动作先进行仿真或规则校验，再由有权限人员确认。
- 处置结果回写 Case，用于阈值、规则、模型和提示版本的离线评测。

### 4.3 四类场景设计

#### 场景一：设备健康与预测维护，P0

典型流程：

```text
温度/振动/电流/PLC 信号进入边缘窗口与特征流
→ Data Hub 形成原始片段、特征、工况和质量证据
→ 3D 定位设备与可维护部件，并联动同类对象对比
→ AskData 解释趋势和相关变化
→ MaintenanceInsight 输出风险区间、RUL 区间和贡献特征
→ 生成点检/诊断/保养/备件 Case 草案
→ 人工确认并同步 EAM/CMMS
→ 维保执行与复检
→ 回填真实故障、根因、处理、更换件和效果
```

首版按“机理/阈值告警 + 统计趋势告警 + Iot-nb 模型告警”三路并行，不把所有故障都包装成一个黑盒分数。优先导入你已经训练好的现场模型；透明规则和 Iot-nb 内置基线用于兜底及回归。数据完整率不足、分布漂移、工况不可比或标签不足时必须降级为状态监测，拒绝确定性风险/RUL。

维护知识入口按当前设备、部件、故障码和工况检索手册、故障树和相似案例，回答中展示来源、版本和适用范围。大模型负责归纳证据与形成诊断/检查草案，不能改写传感器结果、模型输出或伪造根因。

首期交付：Iot-nb 模型包导入器、Edge/Data Hub 特征窗口适配器、在线部署策略、设备/部件健康卡、异常趋势、同类对比、部件级 3D 告警定位、Case、EAM/CMMS 接口、反馈回填、案例知识检索、模型生命周期和影子评测。边缘侧提供单机视图和本地告警，服务端重点提供跨设备/跨产线比较、案例复用和运营统计，避免两端重复建设。

#### 场景二：生产与质量智能，P0

典型流程：

```text
相机/检测设备 → 现有 VisionCenter 运行现场 ONNX 模型
→ ROI + 连续帧/跟踪规则聚合，抑制瞬时误报与重复事件
→ VisionProvider 固化原图、框/分类、置信度、模型版本和推理环境
→ 绑定摄像头、工位、设备、产品、配方、批次和时间窗
→ AskData 关联工艺参数、原料、班次和历史良率
→ 输出原因候选及支持/反对证据
→ 生成复检、隔离批次或调参 Case 草案
→ 人工确认并同步 QMS/MES
→ 回填真实缺陷、误报/漏报、处置和批次结果
```

现有视觉底座已经支持 detection/classification、YOLO/SSD 等输出、图片/视频任务、ROI、阈值、冷却、DirectML/CPU 回退、事件留证和 3D 联动，应在这套实现上增强：

1. 为任务增加 `stationId/productId/recipeId` 上下文映射，并在推理时解析 `orderId/batchId`，避免只绑定场景对象。
2. 将简单冷却升级为 `N-of-M` 连续帧确认、同目标跟踪与事件去重；原始逐帧结果仍作为证据保存。
3. 将原图、框、标签、置信度、模型版本和运行环境设为不可变事实；复检标签、原因、责任和处置以独立 Review 追加。
4. 增加逐类别混淆矩阵、Precision/Recall、漏检/误检、阈值曲线、相机/工位漂移和新旧模型影子对比。
5. 首期继续做好检测与分类；缺陷分割、异常热力图和 OCR 通过新输出适配器后续加入，不为单个模型破坏通用 Manifest。

模型不直接宣布“根因”，除非规则或统计检验达到预先定义的证据门槛。参数调整首版只生成建议，不自动写 PLC。视觉模型训练仍在现有外部训练链完成，平台负责模型包验证、灰度、推理、反馈和退役。

首期交付：现有质量模型接入、模型版本治理、连续帧事件聚合、视觉事件空间定位、工位/产品/配方/批次关联、质量追溯、复检标注、误报漏报回流、关键因素对比、复检/隔离 Case 和 QMS/MES 接口。PPE/安全模型保留已有能力，但不占用本轮质量闭环主验收范围。

#### 场景三：资源配置与物流推演，P1

复用 Factory Flow Plugin，将现有产线和 AGV 能力形成标准工作流：

```text
选择产线/订单/物流网络
→ 读取实际 Cycle、WIP、故障和班次样本
→ 校准仿真模型
→ AI 生成实验草案，不直接生成结论
→ 确定性引擎运行多次实验
→ 比较吞吐、Lead Time、WIP、利用率、瓶颈和置信区间
→ 3D 回放方案差异
→ 人工选择方案并记录结果
```

首版解决“缓冲多大、哪个工位是瓶颈、增加一台设备是否有效、AGV 数量/路线如何影响吞吐”等问题。不进入订单承诺、供应链计划或完整智能排产。

#### 场景四：能耗与排放优化，P1

先做能源透明和异常解释，再做优化建议：

- 将电、水、气、蒸汽和碳因子绑定到园区/车间/产线/设备层级。
- 建立单位产量能耗、空转能耗、峰谷分布和设备基线。
- 识别“产量变化造成的正常波动”和“工况不变下的异常偏差”。
- AskData 解释偏差，预测插件给出短期区间，仿真/规则插件比较启停、负荷和班次方案。
- 优化动作以建议或排程草案输出，经审批后由现有能源/控制系统执行。

首期不建设企业碳核算平台，也不自动闭环控制设备。

### 4.4 商业交付结构

对客户不拆卖一堆技术模块，而按“平台 + 场景包 + 集成服务”交付：

- **平台基础包**：2D/3D 创作、Data Hub、Binding Runtime、发布运行时、账号权限和审计。
- **智能运营包**：智能洞察、受控问数、Case 中心、BIM/视觉 Provider 和评测观测。
- **行业场景包**：设备健康、生产质量为主包，物流仿真、能源分析按需安装。
- **连接与模型包**：企业连接器、私有模型 Provider、现场视觉模型和第三方 EAM/MES/QMS 适配器。
- **实施服务**：资产与数据映射、场景建模、规则/模型校准、试点验收和模板复制。

这样既保留统一产品内核，也允许客户从一个高价值场景起步，不需要先采购和部署一套重型 AI 或数据中台。

## 5. 首期 MVP

建议选择“一条产线 + 1 至 2 类高损失设备 + 3 至 5 台设备 + 10 至 30 个关键可维护单元 + 1 至 2 个视觉质量工位 + 1 条产品/批次链”作为首期样板，不从全厂总览开始。维护对象优先选择故障频率和损失可计算、信号可采、能在 12 周内观察反馈的伺服、电机、气缸、轴承或丝杆等部件；质量对象优先选择缺陷定义稳定、现场模型和复检结果可取得的工位。物流路径和能源表计在第二阶段加入。

### 5.1 MVP 用户故事

1. 设备经理点击告警，在三次交互内看到设备与部件位置、原始片段/特征趋势、工况和同类对比、风险解释、相似案例及检查建议。
2. 质量工程师从缺陷聚合事件进入工位、产品和批次，查看原图、逐帧结果、真实框、模型版本、关联参数与相似历史事件，创建复检/隔离 Case。
3. 复检人员确认缺陷、误报或漏报并填写处置结果，反馈分别进入视觉评测集、质量 Case 和 QMS/MES 引用，不覆盖原始推理证据。
4. 模型管理员导入 Iot-nb 模型包或视觉 ONNX 包，完成契约校验、固定数据集回放和影子评测后，只将通过审批的版本部署到指定设备/工位。
5. 实施工程师描述“把设备温度绑定到 KPI 和 3D 颜色”，系统生成 `BindingDraft`，通过预览、局部接受和撤销完成配置。

### 5.2 MVP 必要数据

| 数据 | 最小字段 |
| --- | --- |
| 资产台账 | equipmentId、maintainableUnitId、parentUnitId、type、model、location、criticality、sceneObjectId、externalAssetRef |
| 测点与采集 | channelId、maintainableUnitId、source/protocol、unit、sampleRate、qualityRule、edgeNodeId |
| 设备遥测 | timestamp、channelId、equipmentId、maintainableUnitId、value/feature、runState、operatingCondition、quality |
| 维护记录 | case/workOrderId、equipmentId、maintainableUnitId、faultCode、rootCause、action、sparePart、start/end、result、reviewResult |
| 生产批次 | orderId、batchId、product、lineId、stationId、start/end |
| 质量事件 | eventId、stationId、equipmentId、productId、recipeId、orderId、batchId、label、confidence、imageRef、modelVersion、inferenceEnvironment |
| 视觉任务上下文 | camera/sourceId、stationId、equipmentId、productId、recipeId、order/batch 解析规则、ROI、连续帧与去重策略 |
| 视觉复检 | eventId、groundTruthLabels、falsePositive/falseNegative、reviewer、reviewedAt、disposition、qmsRef |
| 物流数据 | source/target、cycleTime、queue/WIP、AGV position/status、shift |

如果设备身份、批次关联或时间戳无法对齐，先做数据治理和映射，不应拿大模型补齐不存在的事实。

### 5.3 试点选择评分

候选产线按以下条件打分，优先选择总分高且数据可获得的对象：

| 条件 | 权重 | 合格表现 |
| --- | ---: | --- |
| 业务损失明确 | 25% | 停机、质量或物流问题有历史金额/时长/数量基线 |
| 数据连续可用 | 25% | 关键部件有可解释信号和采样条件，设备/部件/测点键与时间戳可对齐，并有足够历史事件或可执行影子评测 |
| 处置流程明确 | 15% | 告警后谁判断、谁批准、进入哪个外部系统已有责任人 |
| 3D/BIM 可映射 | 10% | 关键设备、工位、摄像头和路径可以绑定稳定对象 ID |
| 结果可在 12 周内观察 | 15% | 有足够事件频率，不需要等待一年才知道是否有效 |
| 现场负责人投入 | 10% | 设备/质量/工艺负责人能每周参与验收和标注反馈 |

任一候选若“数据连续可用”或“现场负责人投入”为零，暂不作为 AI 试点；可以先做静态孪生和数据治理，但不能承诺预测或根因效果。

### 5.4 参考团队

首期 MVP 建议 6 至 8 人的小型纵向团队：产品/方案负责人 1 人、前端与 3D 2 人、后端与数据 2 人、AI/视觉/算法 1 至 2 人、测试与交付 1 人；设备、质量、工艺和 IT/OT 负责人以兼职业务 Owner 方式参与。若同一人覆盖相邻角色可以缩编，但数据映射、算法评测和现场验收不能无人负责。

## 6. 分阶段路线

### 阶段 0：冻结契约与样板数据，2 至 4 周

- 冻结 `StudioAiContext`、`InsightEnvelope`、`EvidenceRef`、`SuggestedAction` 和 `OperationalCase` v1。
- 冻结 Iot-nb 兼容模型包、部署策略、特征窗口和推理证据契约；用同一固定窗口验证新旧运行时输出一致。
- 把现有 BIM、Vision、场景/看板助手注册到 `AiCapabilityRegistry`。
- 将 SQL 模式降级为专家入口，建立 `AskDataPlan` 白名单语义。
- 打通资产 ID、场景对象 ID、数据设备键、摄像头、工位和批次映射。
- 冻结设备 → 可维护单元 → 测点层级、可比设备组、工况字段和边缘/中心数据保留策略。
- 把维修工单、故障码、根因、换件、复检结果整理成首批可回放案例；无法确认的标签明确标记为未知。
- 建立固定样板数据、20 个 BIM/问数问题、20 个维护窗口、按类别覆盖误报与漏报的视觉评测集，以及 5 个仿真实验黄金用例。

退出门槛：任何答案和动作都能回链到真实数据、对象、事件或实验版本；无法取证时明确拒答或降级。

### 阶段 1：设备 + 质量双闭环 MVP，8 至 12 周

- 交付 AskDataPlugin 最小版本、设备健康卡和 Case 中心。
- 交付 Iot-nb 模型包导入、Edge/Data Hub 特征窗口、在线部署、完整率/漂移门禁、本地降级监测和中心侧同类设备比较。
- 打通视觉逐帧结果 → 连续帧/跟踪聚合 → 工位/产品/配方/批次/3D 对象 → 趋势分析 → Case。
- 交付三路告警、领域知识检索和“预警 → 诊断 → 方案 → 执行 → 复检”影子闭环，不自动下发工单或控制设备。
- 交付视觉复检台、新旧模型影子对比、逐类别质量指标和误报漏报回流。
- 完成一个可发布、可回放、可审计的工业样板应用。

退出门槛：代表性任务能连续完成；同一 Iot-nb 模型包和固定窗口在新旧运行时的特征顺序、归一化、分数和门禁结果一致；维护指标按故障类型报告，视觉指标按类别与工位报告；答案 100% 带 Evidence/Trace；复检不修改原始检测证据；零任意 SQL；零未确认控制动作。

阶段 1 结束设置一次正式 Go/No-Go：若数据对齐率、任务成功率、误报率或业务使用频次没有达到双方预先冻结的最低值，只保留已产生的平台与数据资产，停止扩张更多 AI 场景；若通过，再进入物流、能耗和专用模型投入。

### 阶段 2：物流仿真与能耗洞察，6 至 8 周

- 将 Factory Flow 的校准、重复实验、方案对比和报告补成产品级流程。
- 增加单位产量能耗、基线偏差、峰谷和空转分析。
- AI 只生成实验/分析草案，结果由确定性引擎计算。
- 对接一个外部 EAM/QMS/MES 或工单系统，验证 Case 互通。

退出门槛：相同模型、输入和种子结果一致；报告记录模型/数据/实验版本；能耗建议可以回看实施前后效果。

### 阶段 3：规模化复制，6 至 8 周

- 把样板抽成可安装行业模板、数据映射向导和评测包。
- 加入私有模型 Provider、成本/延迟策略和多项目运营观测。
- 根据真实项目再增加声纹、分割、异常热力图、OCR、专用预测模型或优化器。

退出门槛：模板换一组资产和数据映射即可复制，不需要修改编辑器核心或复制一套 UI。

上述周期按已有基础、1 个稳定试点和小型跨职能团队估算。若 M0–M9 的 P0 工程门禁尚未完成，AI 场景应以独立垂直切片推进，不能绕过 `ApplicationDocument`、Binding Runtime、权限和公开 SDK 的整改。

## 7. 验收指标

### 7.1 产品与可信性门禁

| 维度 | 建议门禁 |
| --- | --- |
| 证据 | 分析性答案 100% 带数据/对象/事件/实验引用、版本和 Trace ID |
| 问数 | 零任意 SQL；未知指标、越权对象、质量失败时阻断或澄清 |
| 视觉 | 解释逐项引用真实事件、框、标签、置信度和模型版本 |
| 维护 | 按故障类型报告 Precision、Recall、误报/漏报、覆盖率和提前量分布；完整率、工况可比性或漂移门禁失败时拒绝确定性输出 |
| 仿真 | 相同模型、输入和随机种子产生一致结果；正式结论带重复次数和置信区间 |
| 动作 | 零绕过确认的发布、工单下发或设备控制；所有接受/拒绝/撤销可审计 |
| 降级 | AI/模型 Provider 不可用时，编辑、监控、BIM、视觉事件和仿真仍可独立运行 |

### 7.2 试点业务指标

立项时先采集 4 周基线，再由业务方冻结目标，不预先承诺虚假收益：

- 设备：每设备每日告警量、告警到定位时间、平均诊断/修复时间（MTTD/MTTR）、故障间隔（MTBF）、计划外停机、Precision/Recall、误报/漏报、故障覆盖率、提前量分布、点检效率、备件缺料停机和库存周转。
- 质量：缺陷漏检/误检、批次追溯时间、复检时间、一次合格率、报废与返工。
- 物流：吞吐、Lead Time、WIP、队列、瓶颈利用率、AGV 空驶与等待。
- 能耗：单位产量能耗、空转能耗、峰值需量、异常发现时间、建议采纳后节省量。
- AI：任务成功率、建议采纳率、撤销率、无证据拒答率、p95 延迟、单任务成本。

## 8. 风险与取舍

| 风险 | 处理方式 |
| --- | --- |
| 3D 漂亮但业务闭环为空 | 每个场景以 Case、外部系统动作和结果回填验收，不以大屏截图验收 |
| 数据身份和时间无法对齐 | 先冻结设备键、批次键、对象绑定和时钟；AI 不推测缺失关联 |
| AI 产生错误根因或动作 | 输出原因候选和证据强弱；高风险建议必须人工确认和规则/仿真校验 |
| 专用模型样本不足 | 先用规则/统计基线和影子评测；现场数据满足门槛后再训练专用模型 |
| 场景过多导致产品失焦 | 首期只验收设备维护与生产质量双闭环；物流和能耗通过 Go/No-Go 后再进入 |
| 与 MES/EAM/QMS 重复建设 | iTwin Studio 管上下文、洞察和协同，不复制主数据、工单和生产执行系统 |
| 自动控制带来生产风险 | 首版只读与建议；后续控制也必须白名单、双确认、审计和可回滚 |
| 模型/提示变化导致结果漂移 | 固定 Provider/模型/提示版本，维护离线评测集和失败样本回归 |
| 高频信号把网络与存储压垮 | 原始数据在边缘窗口化和特征化，只按策略上传告警前后片段；容量按测点数 × 采样率 × 保留期测算 |
| 预测准确但现场不采取行动 | 试点前冻结责任人、响应时限、EAM/CMMS 流程和备件策略；以闭环率与业务结果共同验收 |

## 9. 立即执行的五件事

1. 选定一条试点产线和业务负责人，按历史停机损失、事件频率、信号可采性选出 1 至 2 类关键部件，而不是先做全厂大屏。
2. 清点 Iot-nb 现场模型制品、版本、特征、归一化、训练/验证数据指纹和生产资格，先完成一个模型包的兼容导入与固定窗口结果对齐。
3. 用现有 `智造园区综合案例` 扩展出 3 至 5 台设备、10 至 30 个可维护单元、测点与边缘节点、1 至 2 个视觉质量工位和 1 条产品/批次链的可复现样板。
4. 在现有 VisionCenter 上先增加质量上下文、连续帧聚合、复检真值与 Case，不另起视觉项目。
5. 分别以“边缘窗口 → Iot-nb 模型 → 部件级 3D 定位 → 维护 Case → 复检反馈”和“视觉聚合事件 → 工位/批次 → 质量 Case → 复检真值”做两条端到端影子验收。
