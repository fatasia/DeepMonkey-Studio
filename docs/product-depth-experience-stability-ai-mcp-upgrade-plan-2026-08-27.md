# Deep Monkey Studio 深度、体验、稳定性与 AI/MCP 升级计划

评估日期：2026-08-27  
评估对象：`dev-studio` 当前工作树  
对标范围：ThingJS、帆软 FineVis/FineBI/FineReport、Unity 6、山海鲸、图扑软件 HT for Web、西门子 Building X / Teamcenter / Tecnomatix / Industrial Edge。

## 1. 决策摘要

### 1.1 严格结论

Deep Monkey Studio 的问题不是功能不够，而是**功能已经超过当前产品架构和体验系统的承载能力**。

当前项目拥有 BIM/CAD、多格式转换、2D 看板、3D 编辑、数据接入、视觉 AI、工业协议、拓扑、优化器、脚本、XR、桌面端和云渲染等大量能力。这个广度已经可以做强演示，但还没有形成主流商业产品应有的四个闭环：

1. 用户从项目创建到发布运行的连续工作流。
2. 统一、可预测、可撤销的编辑体验。
3. 可量化、可回归的性能与稳定性体系。
4. 面向第三方开发和 AI Agent 的稳定领域接口。

如果继续横向增加功能，项目会越来越像“工具陈列室”；如果先做 12 至 20 周的深度治理，它才可能成为可持续交付的产品。

### 1.2 推荐定位

不要正面复制 Unity，也不要试图覆盖西门子完整的 PLM、仿真、工业边缘和楼宇运营体系。推荐定位为：

> 面向工业运营、仿真验证与工程资产场景的 Web 原生数字孪生应用交付平台。用一套项目模型完成工业数据接入、工程模型与资产融合、2D/3D 创作、仿真与虚拟调试、联动校验、发布和运行诊断，并允许开发者与 AI 在受控边界内扩展。

产品的差异化不应是“功能数量更多”，而应是：

- 比 Unity 更快完成 Web/私有化数字孪生项目交付。
- 比 ThingJS 和山海鲸保留更深的工程模型语义、工业对象映射、模型处理和运行数据能力。
- 比帆软更自然地连接 2D 分析与 3D 对象、空间和实时事件。
- 对照图扑 HT for Web 的同一 DataModel 驱动 2D/3D 和扁平 API 优势，形成更易上手的统一项目对象、页面组件、Unity 资源和脚本控制模型。
- 比西门子体系更轻、更开放、更适合中型项目快速落地，但不伪装成 PLM、CDE 或工程仿真替代品。

#### 功能不是简单删减，而是分层承载

“只有演示价值或无法进入主工作流的功能不进主产品”不作为删功能规则。低频、展示性或阶段性能力只要能帮助售前验证、方案沟通、实施交付、问题诊断或生态扩展，就可以保留；关键是不能与高频任务争夺默认界面、启动资源和用户注意力。

所有能力按价值、频率、成熟度和运行成本放入三层：

| 层级 | 适用能力 | 产品承载方式 | 进入条件 |
|---|---|---|---|
| 主工作流 | 高频且直接影响交付结果 | 默认可见，进入项目后可连续完成 | 有明确任务起点、结果反馈、异常处理和下一步 |
| 二级工具 | 有业务价值但低频或面向特定角色 | 上下文操作、二级页面、折叠区或资源工具 | 可发现、可返回主流程、按需加载且状态不丢失 |
| 插件/实验室 | 探索性、展示性、行业定制或尚未规模验证 | 插件中心、实验室、模板示例；默认关闭 | 标记成熟度和适用边界，不拖累主包、权限与稳定性 |

只有以下能力才应移出产品交付范围：与现有能力重复且没有迁移收益；入口孤立、没有可消费结果；没有权限、错误和审计边界；无法按需隔离并持续拖累默认性能；长期无人维护且不存在客户或实施价值。即便如此，也应先做使用证据和依赖分析，而不是凭“像演示功能”直接删除。

参数化建模按第二层建设：它是项目资源中的轻量资产生成器，用于安装板、支架、垫块等现场适配件的参数化复用，并把参数、语义绑定和版本证据带入数字孪生；它不进入一级导航，也不扩张为 BIM/CAD 编辑器。AI 草案、更多模板和试验性生成器则进入插件层。

### 1.3 MCP 决策

**应该提供 MCP，但不是立刻把现有 REST API 全量包装出去。**

推荐顺序：

1. 先稳定领域命令、查询、权限、版本和事务。
2. 再提供只读 MCP Server Developer Preview。
3. 再开放带“计划 → 预览差异 → 用户确认 → 应用 → 撤销”的写工具。
4. 最后再让平台作为 MCP Client/Host 接入外部系统。

对外提供 MCP Server 的价值很高，因为它允许 Cursor、Claude Code、Codex、企业 Agent 或自研助手理解项目、读取 BIM/场景/数据上下文并执行受控操作。MCP 不能替代 REST/OpenAPI、TypeScript SDK、插件 SDK 和事件 Webhook，它只应是这些稳定能力之上的 AI 适配层。

### 1.4 名称风险

旧候选名“iTwin Studio”与 Bentley 已公开运营多年的 iTwin 产品体系高度重合，因此不再作为产品名称。2026-09-04 的最终品牌决策是 **Deep Monkey Studio**：网页、客户端、安装包、Unity 插件和公开文档统一采用该名称；`@bim-studio`、`bim-studio-api`、环境变量、数据库名和路由继续作为稳定技术标识，不随展示品牌迁移。

### 1.5 本轮正式视觉目标与验收口径

本轮增加三个逐级目标，三者都必须以真实工业资产、同机位截图、帧时间和自动策略日志验收，不能以功能开关数量代替结果：

1. **默认观感超过普通 ThingJS 工业项目**：新场景无需用户调参，即具备中性工业环境、稳定落地阴影、环境反射、轻量间接光、空间接触阴影、抗锯齿和一致色调映射。默认不启用会干扰工程判断的强 Bloom、景深、颗粒或过度饱和。
2. **达到 Unity URP 优质项目的主要视觉层次与自动性能体验**：覆盖 PBR、环境光照、可靠阴影、AO、透明与发光材质、选择轮廓、色调映射、质量分档、帧时间反馈和自动恢复。自动策略优先调整内部渲染分辨率、阴影更新频率和后处理成本，不改写模型几何、材质或纹理，不让用户感知模型质量下降。
3. **接近部分 Unity HDRP 效果**：只建设 Web 端收益高且可稳定回退的能力，包括更高质量阴影、反射/探针、间接光近似、自动曝光与色彩分级、区域光和精选后处理。Nanite、Lumen、虚拟阴影贴图和路径追踪不作为本轮同级承诺。

发布验收至少包含低、中、高三档设备策略、WebGL 与 WebGPU 同场景对比、5% low 帧时间、显存/内存峰值、场景切换恢复和渲染后端回退。只有达到定义的真实资产基准才能标记目标完成；演示方盒、单元测试或理论能力不能单独作为竞品同级证据。

#### 场景视觉与 3D 预制体资源门槛

- 环境资源必须覆盖天空、天气、背景、地面、HDRI、灯光和后处理组合；内置程序化资源断网可用，高清 HDRI/PBR 按需下载并进入本地缓存或离线资源包。
- 工业特效必须覆盖冲击波、扫描环、飞升线、飞线、管线流动、告警光环、信标、电子围栏、路径轨迹和区域热力；每项提供真实预览、性能等级、颜色/速度/范围参数和数据绑定入口。
- 3D 预制体覆盖园区、小区、车间常用对象，包括厂房、道路、围栏、门禁、照明、绿化、人物、车辆、AGV、货架、托盘、传送带、工业机器人、机床、传感器和安全设施。人物、车辆与 AGV 必须支持可视化路线、速度、停靠点、循环/往返、朝向和脚本/数据驱动。
- 内置资源、外部开放库和用户导入资源进入同一资源中心。2D 支持图片、SVG、视频、字体和组件包；3D 支持 GLB/GLTF/FBX/IFC 及既有 CAD 转换结果。导入后必须有预览、校验、去重、版本、依赖、引用统计、删除保护和项目包携带能力。
- 数量不是唯一门槛：模型必须可放入真实工作流，预览与实物一致，默认尺度/原点/材质合理；单个高面数模型需明确性能等级。竞品私有、VIP 或授权不明文件不复制，只使用正常授权或明确开放来源。

- 2D、3D、脚本现共享同一应用/场景上下文：二维顶部可进入关联三维，三维顶部可回到原二维页面或打开脚本；脚本工作区自身也提供二维/三维/脚本切换，二维选中的组件会作为脚本首选挂载目标，脚本标题显式显示当前挂载对象/组件，避免跨工作区后误编辑目标。在线门禁已真实选中二维图层后断言脚本不再回退到“整个场景”，并验证脚本面板内的二维/三维切换；仍需继续补齐多页、多场景和冲突保存场景。
- Unity 0.6.1 插件已把模型显隐/变换、Animator、材质、相机、灯光和可选 uGUI 双向绑定纳入同一 manifest；平台图形化面板和 Worker 脚本 `studio.unity()` 共用属性、动作、对象和场景白名单。2022.3.62f1 与 6000.0.52f1 已通过真实 WebGL 构建、桥注入、manifest 包版本和 Loader/Framework/WASM/Data 完整性门禁；平台另外验证 Brotli/Gzip 响应头与底层 MIME，避免压缩构建导入后启动超时。
- 项目 8 步交付主线已补齐共享就绪口径、必需步骤进度、去重阻断项、阻断直达处理、发布前自动转入校验、上次工作返回和刷新恢复。此前“流程卡显示校验通过、弹窗又因缺少联动阻断”的状态冲突已消除；在线门禁会真实点击未就绪项目的发布步骤并验证其转入可处理的交付校验。

因此，项目不是“没有工程质量”。问题是现有质量证据偏重单元、合同和模块测试，缺少真实浏览器主流程、长时间运行、故障注入、性能趋势和跨版本发布门禁。

### 2.3 页面与交互判断

现有视觉风格克制，暗色中性色与琥珀色强调基本统一，不是廉价模板风格。问题主要在产品层而不是“换一套皮肤”：

- 项目、场景、数据、资源、视觉、优化、系统等入口按技术模块组织，不按用户交付任务组织。
- 编辑器一次暴露太多工具，首次用户缺少明确的下一步，高频与低频能力没有分层。
- 2D、3D、数据、发布之间虽有能力连接，但用户跨模块后缺少统一上下文、进度和错误汇总。
- 大量 7 至 11px 字号和 24 至 34px 控件让界面“看起来紧凑”，实际牺牲了可读性和可操作性。
- 空态、加载态、失败态、离线态和权限态没有形成统一语言。
- 已有发布校验和部分诊断能力，但还不是贯穿全项目的交付门禁。

设计判断：桌面视觉基础约 B-，工作流连贯性约 C-，响应式与可读性约 D+，整体产品体验约 C。这个分数说明“可用但不成熟”，不能支撑高频、长期和规模化交付。

### 3.2 竞争策略

1. **BIM/工业资产进入 Web 应用的时间**：上传、转换、优化、语义检查、使用和发布的总耗时。
2. **2D/3D/数据联动交付效率**：一个业务事件从数据到组件、模型和告警的配置步骤与成功率。
3. **私有化交付完整度**：安装、配置、身份、备份、升级、诊断和回滚是否可由客户团队独立完成。
4. **运行稳定度**：首帧、帧时间、内存、场景切换、断流恢复、脚本隔离和崩溃恢复。
5. **可扩展性**：第三方不修改核心代码，能否用 SDK、API、插件和 MCP 完成真实业务扩展。

## 4. 产品升级方案

### 4.1 重构信息架构，围绕交付任务而不是技术模块

项目内只保留五个一级工作区：

1. **概览**：目标、最近工作、交付进度、阻断项、运行状态。
2. **数据与资产**：连接、数据集、模型、图片视频、转换、优化和版本。
3. **设计**：页面、场景、拓扑、组件、布局和复用资产。
4. **联动与自动化**：变量、过滤、事件流、脚本、AI 生成内容和调试记录。
5. **校验与发布**：依赖、权限、性能、兼容、差异、审批、发布、回滚和运行诊断。

视觉 AI、云渲染、数据协议和系统设置不应抢占普通用户一级导航。它们应根据项目能力、用户角色和当前任务在对应工作区出现。

### 4.2 建立三层复杂度

| 模式 | 面向用户 | 默认体验 |
|---|---|---|
| 简单模式 | 项目经理、实施人员 | 向导、模板、推荐默认值、少量必填项 |
| 专业模式 | BIM、数据、可视化工程师 | 完整属性、联动、诊断、版本和性能控制 |
| 开发者模式 | 插件开发者、AI Agent | SDK、脚本、API、MCP、日志、权限和契约测试 |

这不是三套产品。三种模式共享同一 `ApplicationDocument`、命令、权限、版本和发布运行时，只改变信息密度与入口。

### 4.3 固定八步用户主流程

```text
创建项目
  → 选择交付模板
  → 接入数据与资产
  → 设计 2D/3D
  → 配置联动
  → 校验
  → 发布
  → 运行与迭代
```

每一步都必须显示：当前状态、下一步、阻断原因、回到上一步后是否保留上下文、谁有权限处理。

### 4.4 统一关键交互

- 所有编辑操作进入统一命令系统，支持撤销、重做、批量、事务和操作历史。
- 自动保存显示“保存中、已保存、保存失败、存在冲突”，不能只显示模糊状态。
- 选择对象后只显示与当前任务有关的属性；高级属性折叠，不让右侧面板成为字段仓库。
- 对话框只用于短任务；超过两个步骤的配置使用抽屉或独立工作区。
- 错误信息必须包含“发生了什么、影响什么、下一步怎么做、打开诊断”。
- 删除优先提供软删除或短期撤销；发布、控制设备和数据写入必须明确二次确认。
- 统一命令面板支持“打开页面、定位对象、运行校验、查看错误”，减少层级导航成本。

### 4.5 建立可复用资产系统

向 Unity Prefab 和 Addressables 学习“复用和依赖”，但保持 Web/BIM 范围：

- Component Definition：可复用的 2D/3D 组件定义。
- Variant：行业或状态变体。
- Instance Override：场景实例的局部覆盖。
- Resource Dependency Graph：模型、材质、贴图、脚本、数据集、字体和视频依赖。
- Version + Migration：组件版本和升级预览。
- Usage：资源被哪些项目、页面和场景引用。

没有这套能力，模板、AI 生成和第三方插件都会不断复制不可维护的对象。

## 5. 技术升级方案

### 5.1 先收敛事实源和写入模型

目标：`ApplicationDocument` 成为设计态唯一事实源。

- 删除长期并存的 `SceneSnapshot` 编辑路径，只在必要的运行时/导出边界生成快照。
- 所有写入使用版本号或 ETag，冲突时返回可解释的差异。
- 保存、发布、资源引用更新必须原子化；失败时线上版本不变化。
- 命令必须包含 `commandId`、`expectedRevision`、操作者、来源、时间和可撤销信息。
- AI、MCP、UI、插件都调用同一领域命令，不允许各自绕过验证器写文档。

### 5.2 拆分前端运行边界

不是为了“文件变小”而拆文件，而是按故障、加载和团队所有权拆边界：

- `StudioShell`：路由、会话、项目上下文、全局错误边界。
- `DashboardWorkspace`：2D 文档、画布、组件和分析。
- `SceneWorkspace`：3D 场景和编辑状态。
- `DataAssetWorkspace`：数据、资产、转换和优化。
- `AutomationWorkspace`：交互、脚本、AI 和调试。
- `ReleaseWorkspace`：校验、发布、版本和运行诊断。

`ViewerEngine` 拆为 renderer、scene graph、selection、camera/controls、measurement、clipping、animation、physics、effects、resource lifecycle 等子系统，并通过窄接口组合。物理、XR、后处理、Monaco、优化器和视觉中心全部按能力懒加载。

### 5.3 建立设计系统门禁

- 建立颜色、间距、字号、行高、圆角、阴影、层级和动画 token。
- 桌面应用正文不低于 12px，关键操作和表单建议 13 至 14px；7 至 9px 只允许极少数非关键信息或画布缩放后的装饰标签。
- 桌面控件常规高度至少 32px，触控目标至少 44×44px。
- 支持 100%、125%、150% 缩放和 1280、1440、1920、4K；小于 768px 明确进入浏览/审批模式，不强行塞入完整专业编辑器。
- 页面级错误边界、骨架、空态、离线态和无权限态使用统一组件。

### 5.4 性能工程

第一步不是直接定“必须 60 FPS”，而是冻结参考设备、浏览器、资产和工作负载。建议建立 R1 至 R6：

| 场景 | 目的 |
|---|---|
| R1 项目管理空载 | 测首屏、导航和基础包体 |
| R2 100 MB GLB/IFC | 测转换后首帧、拾取和属性 |
| R3 多模型 5M 三角面 | 测帧时间、显存、剖切和选择 |
| R4 300 个 2D 组件 | 测画布编辑、绑定和发布运行 |
| R5 实时数据 + 视频 + 告警 | 测重连、背压、长时间运行 |
| R6 20 次场景切换 + 短时稳定性门禁 | 测内存、句柄、WebGL context、设备丢失和恢复 |

首批预算：

- 管理页初始 JS gzip 不超过 350 KB。
- 未进入 3D 时不下载 Three、Rapier、IFC、优化器和 Monaco。
- 普通 UI 操作 INP p75 小于 200 ms，画布选择/拖动 p95 小于 100 ms。
- 参考场景首个可交互画面 p75 小于 3 秒，具体模型加载另报进度。
- 20 次场景切换后 JS heap 和 GPU 资源回落到稳定值的 105% 以内。
- 每个发布包记录首帧、P95 帧时间、长任务、峰值内存、实际渲染后端和降级原因。

#### WebGPU 一级对比门槛

WebGPU 不再只是“三维性能”中的一个实现开关，而是与 WebGL 2、Unity Release Player 并列的一级验收项。R1 至 R6 必须分别保存冷/热首帧、管线编译尖峰、P50/P95/P99/最大帧、CPU/GPU 时间、Long Task、显存/堆趋势、设备丢失恢复和同画质截图；WebGL 的结果不能替代 WebGPU 短时资源与恢复证据。带 GPU 的验收机必须执行严格入口 `pnpm gate:webgpu`，环境缺失与产品初始化失败分别判定。WebGPU 只有在 R1–R5 至少四项 P95 改善 15%、其余不退化超过 5%，且画质、功能与目标设备矩阵通过后才能成为 Auto 默认；理论峰值、空场景 FPS 或单个 Demo 都不作为发布依据。Unity 于 2026-08-24 宣布从 6000.6 起把 WebGPU Web 后端移出实验状态；截至 2026-08-30，6000.6 仍处于 Beta 发布序列，因此它进入一级路线对照，但不能被写成稳定版成熟度证据。本机已有 6000.0 仍只作为既有 WebGL Bridge 证据；公平性能测试需冻结并记录具体 6000.6 Beta/正式版本。完整夹具、画质指标和 Three WebGL/WebGPU 与 Unity 隔离对照见 [渲染性能基准](./rendering-performance-benchmark.md)。

#### 自动性能治理，而不是让用户手工调参

默认发布策略改为“智能自动”，但自动策略必须完整保留建模师确定的模型、材质、纹理、LOD、阴影和后处理效果。平台先消除运行时浪费，再扩展渲染能力；不能用静默降画质冒充性能提升。普通用户不需要理解剔除、批次、缓存或编码参数，专家模式仅用于诊断和受控覆盖。

1. **发布前无损编译**：保留原始资产和作者 LOD，自动执行可逆的 Meshopt/Draco 传输压缩、无视觉差异的纹理转码、实例候选、空间索引、BVH、材质复用、分块和管线预热；任何会改变画面的处理只生成建议，不自动写入发布包。
2. **启动时自动预检**：根据 GPU/浏览器能力、物理像素、内存、场景统计和高耗特性生成设备与场景预算，自动选择 WebGPU 或 WebGL，不把后端名称暴露成普通用户必须理解的选项。
3. **运行时无损治理**：使用可见帧 P95/P99、输入延迟、Long Task、draw call、三角面、纹理、heap 和设备丢失作为证据，自动启用视锥/遮挡剔除、不可见动画延迟求值、实例与批次复用、主线程任务分片、最新帧合并、缓存、资源回收和管线预热。模型效果、像素比、作者 LOD、阴影与后处理不参与自动降级。
4. **业务与画质保护**：标签、告警、选中态、测量、关键设备、数据正确性和作者视觉效果不能被自动性能策略关闭；每次调度调整必须记录触发证据、执行动作、恢复条件和当前预算。
5. **云端建议而非静默迁移**：本地设备持续无法满足目标且网络、GPU 容量、权限和成本策略均通过时，平台提示一键切换云渲染；会话中不得因短时抖动静默迁移。本地、云端和回退模式使用同一不可变发布包。

原“极速模式”的有损行为已废止：发布数据中的 `fast` 仅作为旧场景兼容值，界面统一显示“自动优化”。渐进 GLTF 必须最终升级到完整精度，天气、灯光、阴影、反射、全局光照、后处理和物理仿真保持作者配置。当前自动守卫只在至少 120 帧样本、连续三个 P95 ≥ 25 ms 的压力窗口后，以 5% 步长临时调整填充率，最多降低 10% 且不低于 1×；连续健康窗口后恢复设备基准像素比。该实现是质量保护基础，不代替 R1 至 R6 的正式对照验收。

2026-08-30 已新增两项无损运行时治理：模型、材质、环境和灯光变更会合并后在空闲窗口异步预热渲染管线；设备方盒等基础几何按查看器复用 GPU 顶点/索引资源，仍保留每个对象的独立材质、变换、拾取和脚本语义。固定 120 对象门禁中 WebGL 几何资源由历史 122 降为 8，并设置不超过 10 的回归门槛。BIM 空间覆盖层也改为每模型只计算一次世界矩阵、未变化不传播，修复手动矩阵对象随模型变换不精确的问题。以上结果不代表实例化或批处理完成，draw call 仍需后续在不破坏独立对象语义的前提下降低。

### 5.5 稳定性与可运维性

- Playwright 覆盖“建项目 → 接数据 → 导模型 → 设计 → 联动 → 校验 → 发布 → 回滚”。
- 固定视口视觉回归覆盖 1280、1440、1920、4K 和 125% 缩放。
- 故障注入覆盖 API 500、数据库超时、对象存储失败、WebSocket 断流、模型转换超时、GPU context 丢失、脚本死循环和磁盘满。
- 建立结构化日志、trace ID、前端错误、API 延迟、队列长度、转换耗时、模型加载阶段、帧时间和内存趋势。
- 转换、视觉推理和云渲染使用持久任务状态、并发配额、取消、超时、重试和失败清理。
- 每个版本有数据库/对象存储备份验证、升级演练和回滚演练。

建议 SLO：

- crash-free session ≥ 99.5%。
- 核心 API 成功率 ≥ 99.9%，不含明确的 4xx。
- 自动保存成功率 ≥ 99.9%，异常退出最多丢失 5 秒已确认编辑。
- 发布事务失败时线上版本零变化，历史版本 100% 可回滚。
- P0 数据损坏和跨项目越权为 0。

## 6. AI 开发能力规划

### 6.1 两类用户，两种入口

**业务用户的内嵌 Copilot**：在当前项目内完成解释、诊断、生成草案和辅助配置。  
**开发者的外部 AI 接入**：通过 SDK、API 和 MCP 让外部 AI 编码工具理解并修改项目。

两者共享同一上下文、权限、命令、审计和评测系统，不能各写一套 AI 逻辑。

### 6.2 AI 最有价值的首批任务

按价值和可验证性排序：

1. 解释当前选中构件、数据绑定和告警依据。
2. 诊断断开的资源、字段、联动和发布阻断项。
3. 从自然语言生成看板/场景/联动的结构化草案。
4. 生成脚本，但只使用公开 SDK，并先通过类型、权限、预算和沙箱测试。
5. 将一组模型、页面或绑定变更转成可预览差异。
6. 为性能问题定位大模型、过量 draw call、重复材质、重组件和高频脚本。
7. 生成项目文档、交付清单、接口映射和回归用例。

不应首批开放：任意 SQL、任意 Shell、任意网络、直接控制真实设备、无确认发布、绕过 SDK 修改内部 JSON。

### 6.3 AI 交互闭环

所有可写 AI 操作固定为：

```text
理解意图
  → 收集最小上下文
  → 生成结构化计划
  → 校验权限与依赖
  → 预览差异和影响
  → 用户局部接受/拒绝
  → 原子应用
  → 可撤销、可审计、可复现
```

模型输出不是事实源。命令验证器、文档 schema、权限和运行时才是事实源。

## 7. MCP 方案

### 7.1 产品边界

需要明确两个方向：

- **平台作为 MCP Server**：让外部 AI 使用平台能力。优先做。
- **平台作为 MCP Client/Host**：让平台内 AI 调用企业外部 MCP Server。后做。

首版只做 Server。若两边同时做，身份、授权、上下文、审计和故障面会翻倍。

### 7.2 MCP 不是业务层

推荐架构：

```text
UI / TypeScript SDK / REST / MCP
              ↓
       Application Service
              ↓
 Query Service + Command Service + Policy + Audit
              ↓
 ApplicationDocument / Data / Asset / Runtime
```

MCP adapter 只做协议转换、schema 暴露、授权映射和结果裁剪。它不能直接读取数据库文件、调用 `ViewerEngine` 私有方法或修改 `ApplicationDocument` JSON。

### 7.3 首版能力

#### Resources

- `bim://projects/{projectId}/summary`
- `bim://applications/{applicationId}/document`
- `bim://scenes/{sceneId}/hierarchy`
- `bim://models/{modelId}/property-schema`
- `bim://datasets/{datasetId}/schema`
- `bim://publications/{publicationId}/validation-report`
- `bim://sdk/{version}/documentation`

大模型、图片和视频不直接塞入上下文，只返回元数据、分页结果和受控下载资源。

#### Read tools，Developer Preview

- `projects.list`
- `project.get_summary`
- `application.get`
- `scene.search_objects`
- `scene.get_selection_context`
- `model.get_properties`
- `dataset.get_schema`
- `dataset.preview`
- `delivery.validate`
- `performance.inspect`
- `audit.list_recent`

#### Write tools，后续 Beta

- `change.plan`
- `change.preview`
- `change.apply`
- `change.undo`
- `asset.start_conversion`
- `application.create_draft`
- `publication.prepare`
- `publication.publish`

不要为每个内部 API 生成一个 MCP tool。工具应面向用户意图，并维持 15 至 25 个稳定工具；低级对象操作放到 `change.plan/apply` 的类型化命令集中。

### 7.4 安全与稳定要求

- 远程 MCP 使用 Streamable HTTP；本地开发可提供 stdio。
- 远程授权按 MCP 当前规范采用 OAuth 2.1、PKCE、受保护资源元数据和 token audience 校验。
- 权限至少拆为 `project.read`、`scene.read`、`data.read`、`asset.write`、`application.write`、`publication.write`、`operation.control`。
- 禁止 token passthrough；平台访问下游系统时使用独立凭据。
- 所有写工具要求 `idempotencyKey`、`expectedRevision`、`dryRun`、差异摘要和审计记录。
- `publication.publish`、设备控制和数据写入永远需要显式确认，不接受模型单方面批准。
- 限制分页、结果大小、执行时间、并发和单位时间调用次数。
- 返回结构化错误码、可修复建议和 trace ID，不把堆栈或密钥暴露给模型。
- MCP `2026-07-28` 已采用无状态核心，`initialize/initialized` 被 `server/discover` 和逐请求元数据取代；远程入口必须校验 `MCP-Protocol-Version`、`Mcp-Method` 和工具名路由头，同时保留受控的旧客户端兼容。
- Tasks 已迁出核心成为 `io.modelcontextprotocol/tasks` 扩展。首版仍不把转换/优化任务的可靠性绑定到该扩展，先返回平台自己的 job ID 和状态资源。

### 7.5 MCP 上线门槛

满足以下条件才发布写工具：

1. `ApplicationDocument` 单一事实源完成。
2. 命令可校验、可预览、可撤销、可审计。
3. OAuth scope 与项目角色完成映射。
4. 50 个代表性 AI 编辑任务离线评测通过率 ≥ 90%。
5. 100% 写入均带预期版本，冲突不会静默覆盖。
6. 发布、设备控制、数据写入 100% 经过确认门。
7. 外部客户端兼容测试覆盖至少三个主流 MCP Client。

- 建立新的五工作区信息架构原型。

退出门槛：核心用户能在原型中不跳出项目完成八步主流程；每个现有入口都有明确归属。

### Phase 1，3 至 6 周：可信编辑与主流程

- 统一字号、控件、空态、错误态、保存态和权限态。
- 高频能力默认展示，XR、物理、后处理、脚本等进入高级/开发者模式。
- Playwright 覆盖八步主流程。

退出门槛：新用户能在无口头指导下完成“模板 → 数据 → 场景 → 联动 → 发布”；保存故障不会产生半成功状态。

### Phase 2，7 至 12 周：性能、稳定和专业深度

交付：

- `ViewerEngine` 子系统拆分和能力懒加载。
- 管理、数据、2D、3D、脚本、优化器路由级分包。
- R1 至 R6 性能仪表与 CI 预算。
- 可复用 Component Definition / Variant / Instance Override。
- 统一联动调试器、数据语义字段、参数、过滤、钻取和权限。
- 故障注入、短时资源与恢复门禁、备份恢复和发布回滚演练。

退出门槛：构建无未豁免大包告警；R1 至 R6 预算通过；20 次场景切换无持续资源增长；核心流程 crash-free ≥ 99.5%。

### Phase 3，13 至 16 周：开发者平台与只读 MCP

交付：

- 稳定 Query Service、Command Service、Policy 和 Audit。
- OpenAPI、TypeScript SDK、Webhook、插件模板和开发者中心。
- 只读 MCP Server，支持 stdio 与 Streamable HTTP。
- OAuth 2.1、scope、租户/项目隔离、速率限制和兼容测试。
- 50 个 AI 任务、30 个问数问题和 20 个诊断任务评测集。

退出门槛：第三方示例不导入私有路径即可完成“读取项目 → 查构件 → 查数据 → 运行交付校验”；零越权和零未审计调用。

### Phase 4，17 至 20 周：可写 MCP 与 AI 共创

交付：

- `change.plan/preview/apply/undo`。
- AI 生成页面、场景、绑定和脚本草案。
- 局部接受/拒绝、差异视图、原子应用和撤销。
- 发布准备工具；发布、设备控制和数据写入保留强确认。
- 外部 MCP Server 接入仅做技术预研，不进入默认产品。

退出门槛：代表性编辑任务通过率 ≥ 90%，100% 变更可追踪，100% 冲突不静默覆盖，100% 高风险动作需要确认。

四条并行工作流足够，不建议同时成立更多小组：

## 10. 必须停止的做法

- 停止用 README 功能数量代表产品成熟度。
- 停止新增没有主流程归属的一级入口。
- 停止在 `App.tsx`、`ViewerEngine.ts` 和单体 CSS 中继续堆能力。
- 停止把“有连接器名称”写成“已生产支持”；必须有连接、重连、鉴权、背压和故障证据。
- 停止用空场景 FPS 宣称 WebGPU 或渲染性能领先。
- 停止让 AI 直接生成并执行任意脚本、SQL 或内部 JSON。
- 停止将 MCP 当成 SDK、权限系统或领域模型的替代品。

## 11. 管理层每周只看这些指标

1. 主流程完成率与中断点。
2. 从建项目到首个可发布版本的中位时间。
3. 发布校验一次通过率。
4. crash-free session、自动保存成功率和发布回滚成功率。
5. R1 至 R6 的首帧、P95 帧时间、内存和场景切换残留。
6. 每周新增代码进入 `App.tsx` / `ViewerEngine.ts` 的行数，应持续为负或接近零。
7. 7 至 11px 字号存量和大于预算 chunk 数量，应持续下降。
8. AI 建议采纳率、撤销率、校验失败率和越权拦截数。
9. SDK/MCP 任务成功率和破坏性变更数量。

## 12. 最终判断

未来一个版本的主题应该是：**从“功能广”升级为“交付深”**。

正确顺序是：

```text
主流程与事实源
  → 体验一致性
  → 性能与稳定门禁
  → SDK/API
  → 只读 MCP
  → 可写 MCP 与 AI 共创
```

这样做之后，产品不会在所有维度超过 Unity、帆软或西门子，但会在一个足够清晰的市场位置形成竞争力：用比重型工业平台更低的成本和更短的时间，交付具有工业资产语义、仿真验证、工程模型上下文、2D/3D 联动、私有化运行和可扩展开发能力的数字孪生应用。

## 15. 目标产品边界

### 15.1 产品主张

推荐将产品主张收敛为：

> 连接工程模型、工业数据和确定性仿真，以可追溯 AI 完成资产诊断、虚拟调试、运行问数与专业模型分析的轻量工业数字孪生平台。

首个稳定版本只证明四个闭环：

1. **设备异常到维护行动**：数据就绪检查 → 健康评估 → 故障证据 → RUL 区间 → 处置建议 → 工单/案例。
2. **设计到虚拟调试验收**：信号映射 → 用例/故障矩阵 → SIL 运行 → 时间线回放 → 基线比较 → 验收报告。
3. **自然语言到可信事实**：问题 → 语义计划 → 歧义澄清 → 权限与口径校验 → 确定性执行 → 证据与对象定位。
4. **电池资产到健康孪生**：数据格式识别 → 域与质量判断 → SOC/SOH/RUL → 工况推演 → 基线/候选对比 → 受控报告。

其余能力只有能增强上述闭环时才进入当前版本。

### 15.2 BIM 的明确定位

BIM 增强范围：

- IFC/Revit/工程模型的导入、转换、优化、联邦加载和版本比较。
- 稳定对象身份：`IFC GlobalId / Revit UniqueId / sourceId → engineeringObjectId → assetId → deviceId/tagId → ontologyObjectId`。
- 空间、系统、类型、属性、文档、告警、工单、仿真对象和数据点位的关联。
- 构件搜索、隔离、剖切、测量、属性检查、问题定位、版本差异和运行状态着色。
- AI/问数/维护/调试结果可定位回 2D、3D、拓扑和证据时间线。

明确不做：族/参数化构件建模、钢筋/机电深化、施工图出图、通用几何建模、Revit/Archicad 替代品。BIM 在本产品中是工程上下文，不是产品中心。

## 16. 统一插件架构

### 16.1 不建立第二套插件系统

主工程已有 `packages/plugin-runtime`、`DataNodePlugin`、Scene Extension、Converter Plugin 和 `factory-flow-plugin`。AI 插件化应扩展现有运行时，不再建立独立的“AI 插件管理器”。

建议给 `PluginManifestV1` 增加两类扩展点，并升级为向后兼容的 Manifest v2：

| 扩展点 | 责任 | 示例 |
|---|---|---|
| `ai-provider` | 提供 LLM/多模态模型调用，负责模型能力、限流、成本和健康状态 | OpenAI-compatible、本地模型、企业模型网关 |
| `capability-provider` | 提供确定性的领域查询、分析、仿真或建议能力 | Data Hub 查询、预测维护、虚拟调试、电池健康 |

AI Runtime 只负责编排，不持有具体领域算法。领域插件也不能直接操作 React、`ViewerEngine`、数据库文件或 `ApplicationDocument`。所有修改必须返回类型化 `SuggestedAction`，由宿主的 Command Service 校验、预览和应用。

### 16.2 两种默认运行方式

| 运行方式 | 适用能力 | 默认约束 |
|---|---|---|
| `in-process` TypeScript | 轻量语义规划、规则、格式识别、纯计算 | 无私有深层导入；同步任务有耗时预算 |
| `worker` TypeScript/ONNX/WASM | 离散事件、批量特征、SIL 仿真、电池推理和较重分析 | 可取消、内存/CPU/时间上限；崩溃不影响主线程；不阻塞 Node 或浏览器主线程 |

远程企业模型或 LLM 通过现有 API Gateway/`ai-provider` 访问，不作为本地 sidecar 安装。MCP 不作为内部插件协议；MCP 是稳定领域能力面向外部 AI Client 的适配层。

### 16.3 统一调用与证据契约

每次能力调用必须包含：

```text
CapabilityRequest
  requestId / projectId / applicationId / principal / locale
  capabilityId / capabilityVersion
  selectedObjectRefs / datasetRefs / timeRange
  input / dryRun / expectedRevision / deadline
```

每次返回必须统一为：

```text
CapabilityResult
  status: completed | needs-input | blocked | unavailable | failed
  output
  decisionStatus: production | shadow | research-candidate | insufficient-data
  confidence + interval
  evidence[] + dataLineage[]
  modelOrRuleVersion + pluginVersion
  warnings[] + suggestedActions[]
  traceId + durationMs + generatedAt
```

`suggestedActions` 只允许引用公开领域命令。设备控制、发布和真实数据写入不得由插件直接执行。

### 16.4 插件治理页

系统设置新增“能力插件”，但普通用户不直接面对技术清单。管理员可查看：

- 启用状态、版本、来源、签名和兼容性。
- 提供的能力、权限、数据范围和外部网络要求。
- Worker/模型健康、冷启动、最近错误、P50/P95 延迟和资源占用。
- 当前模型/规则/语义版本、生产/影子/候选状态。
- 黄金用例、回归评测、漂移、撤回和回滚状态。

插件安装失败、Worker 崩溃或模型缺失，只降级对应能力，不能阻断项目编辑、查看和发布。

## 17. 三项自研能力的抽取与集成清单

### 17.1 FATHOM：明确不集成

经对比，FATHOM 与主工程已有 Data Hub、数据连接、数据集、管道、SQL 助手、运营分析、权限和审计存在结构性重叠。继续引入会产生第二套数据控制面、语义版本、连接器和治理 UI，增加部署与维护成本，却不能直接改善核心工业闭环。

决策：

- 不迁移 FATHOM 的代码、模型、FastAPI 服务、Vue 页面、数据库 schema、ONN 或 Agent Mesh。
- 不新增 `semantic-intelligence-plugin`，也不把 FATHOM 作为 MCP 后端。
- 保留“可信问数”产品需求，但在主工程内以最小能力实现：查询意图 → 字段/数据集校验 → 只读执行 → 证据与 trace；只维护设备、测点、指标、空间/产线、维护事件五类轻量映射，不建设全企业本体、图谱编辑器或独立治理后台。
- 语义字段、指标别名和对象映射优先扩展现有 `DataDatasetRecord`、`DataComputedField`、`ApplicationDocument` 和资产映射，不复制 FATHOM 的对象网络。
- 如果未来确实需要跨系统本体，再以外部集成连接器评估，不进入本次升级目标。

AI 变更确认同步简化：普通问数、解释、诊断和只读分析直接返回结果，不进入审批流；场景、脚本、数据映射和发布状态等可逆项目写入，只展示一次“变更摘要 + 校验结果 + 应用/取消”。确认记录复用现有审计，不建设独立审批中心，不提供审批队列、审批角色和多级流转。真实 PLC 写入不是“AI 审批”，仍沿用独立受控命令通道，不与普通 AI 交互混在一起。

### 17.2 IoT-NB：预测维护插件

目标包：`packages/asset-health-plugin`。

抽取并重构：

- 特征窗口、质量率、均值/方差/RMS/峰峰值/峭度/趋势等可解释特征。
- 健康分、故障模式、证据列表、RUL 区间、置信度和数据不足状态。
- 模型/阈值版本、人工反馈、漂移分数与治理状态。
- 基线模型训练/导入的输入输出契约和生产资格门禁。

必须修正的边界：IoT-NB 当前预测维护属于可解释基线，不能包装成针对任意设备都有效的生产模型。首版应支持“规则/统计基线 + 已验证外部模型插件”，并在页面明确区分：演示数据、现场数据、已校准、未校准、生产、影子。

### 17.3 IoT-NB：虚拟调试插件

目标包：`packages/virtual-commissioning-plugin`；运行时统一为浏览器 Web Worker 或服务器 Node Worker。

抽取并重构：

- 固定周期确定性调度思想、固定随机种子、单步、暂停、重放和状态快照。默认目标周期可配置为 50ms，但必须记录实际抖动，不能表述为硬实时保证。
- 信号生成、丢包/延迟/抖动/断线/冻结/坏质量等故障注入。
- 用例生成、断言、基线/当前结果比较、证据时间线和验收报告。
- PLC/HMI/SCADA 信号映射、联锁、幂等、审批、变更单与双阶段审计契约。

运行边界：

- Web Worker/Node Worker 只声明为 SIL 或离线虚拟调试，不宣称硬实时。
- IoT 异步流与确定性仿真流继续严格分离；网络、数据库和 LLM 不得进入关键周期。
- 现场协议复用主工程 API/Data Hub 已有的 OPC UA、S7、Modbus 等 TypeScript 连接器，不迁入 IoT-NB Edge Agent 和 Rust 驱动。
- 真实 PLC 默认只读。任何写入必须经过全局开关、源开关、审批人、变更单、幂等键和审计；AI 无权批准自己提出的写入。现场写入不进入确定性 SIL Worker，由独立受控命令通道处理。

IoT-NB 的物流仿真已经按 `ADR-0008` 独立抽取，继续由 `factory-flow-plugin` 演进，不与虚拟调试内核合并。

### 17.3.1 虚拟调试的价值判断

**结论：保留为核心产品支柱，优先级高于泛化 AI 助手和更多 3D 特效。**

虚拟调试的付费价值不是“看起来像设备在运动”，而是把控制程序、I/O、设备状态和验收证据提前闭环：

| 价值来源 | 客户结果 | 平台必须交付的证据 |
|---|---|---|
| 减少现场联调 | PLC 程序和 HMI 在设备到场前发现大部分逻辑错误 | 信号映射、周期、状态转移和失败断言 |
| 缩短交付周期 | 把 FAT 前置为可重复的 SIL 回归包 | 用例版本、固定种子、重复运行哈希和报告 |
| 降低停线风险 | 在安全环境复现丢包、卡滞、超时、传感器坏质量和联锁故障 | 故障注入参数、时间线、受影响对象和回退动作 |
| 支持变更管理 | 程序、参数或模型变更能与上一个版本比较 | 基线/当前差异、审批、责任人和审计记录 |
| 形成服务收入 | 交付团队可以把测试包、验收报告和诊断案例带到客户现场 | 可导出、可重放、可签字的证据包 |

适用客户：离散制造、产线设备、物流单元、包装/装配、能源与储能控制等存在 PLC/HMI/SCADA 联调的项目。若客户只有静态 BIM 展示、没有控制逻辑或 I/O 约束，虚拟调试不是优先能力。

首版必须做到：

- I/O 映射和状态机可检查，至少支持启动、停止、急停、复位、故障和恢复链路。
- 用例可由模板和 AI 生成，但必须转换成结构化断言；AI 不直接执行控制逻辑。
- 支持单步、暂停、倍速、确定性回放、故障注入、基线比较和 HTML/JSON 证据报告。
- 失败定位到信号、逻辑节点、设备/工程对象和时间点，而不是只显示“测试失败”。
- 逻辑结果与帧率、页面是否打开和 3D 动画完全解耦。

明确不做：

- 不把它包装成实体 PLC、硬实时控制器或已经完成 HIL/FAT 的证明。
- 不首期建设完整机器人动力学、碰撞物理、WMS/APS、人员安全认证或所有厂商 PLC 指令集。
- 不允许 AI、脚本或仿真 Worker 直接向真实 PLC 写入；现场写入始终走独立审批命令通道。

价值门槛：如果一个版本不能让实施人员拿到“可重放的失败证据和验收报告”，就不应把新增仿真对象或视觉效果列为虚拟调试进展。

### 17.3.2 IoT-NB：轻量参数化资产生成

**定位：已按第二层工具落地，不扩张为 CAD/BIM 编辑器。** 它解决的是现场支架、安装板、垫块等规则零件反复建模、参数不可追溯、生成资产与点位/仿真信号脱节的问题。默认入口位于模型资源工作流，AI 只生成可审查草案，不能绕过预览、验证和保存确认。

已实现的高价值链路：

- 使用受限参数、特征和表达式 DSL；禁止 `eval`、任意脚本、文件系统和网络访问，同一定义得到确定性结果。
- OpenCascade 通过浏览器 Worker 按需加载，在独立线程完成精确 B-Rep、布尔运算和 STEP 导出；主线程只接收进度、预览网格、统计和结构化错误。
- 首批提供安装板、支架和垫块三类模板；生成结果保存为不可变 STEP 资源版本，记录定义、参数、内核版本、构建统计、来源版本和替代关系。
- 参数化资源可绑定项目中真实存在的数据集字段、设备点位和仿真信号；保存前校验项目归属和引用有效性，不把连接密码或自由文本执行逻辑写入模型元数据。
- `bim.ai.parametric-draft` 作为独立 AI 插件调用可替换 Provider；输出必须重新经过同一 DSL 校验，并以“研究候选”进入预览，不自动构建、不自动保存。
- 参数化工作台、Worker、OCCT、IFC/Fragments 和后处理均维持能力级懒加载，不进入一级导航和普通页面首屏。

OpenCascade WASM 当前原始体积约 22.97 MB、gzip 约 7.31 MB。它包含 STEP/B-Rep/布尔/倒角等完整 OCCT 几何内核，体积不能与普通前端组件比较；当前门禁是原始体积不超过 25 MB、仅用户打开参数化工作台后请求、失败不影响主应用。只有真实下载或内存数据证明它仍是主要瓶颈时，才评估维护成本较高的自定义裁剪内核。

明确不引入第二套 PythonOCC/OpenCascade 服务，不把 CadQuery/build123d、网格修复、科学求解器或图生 3D 模型塞入在线主路径。它们如有价值，应通过离线工具或实验插件消费同一 STEP/网格资产契约。

### 17.4 分子元宇宙：电池智能插件

目标包：`packages/battery-intelligence-plugin`；首期模型运行时复用现有 `battery-model-service`，后续可按模型切换为 API 侧 `onnxruntime-node` Worker。

直接迁移/整理：

- Arbin、Neware、Maccor、BatteryArchive、CALCE、NASA、BioLogic 和通用表格的格式识别与字段映射。
- `BatteryModelGateway` 请求/响应、取消、超时、健康检查和可用性降级；保持传输层可替换，避免 UI/MCP 绑定 Python 或 ONNX 实现。
- 集成三个正式标准模型，同时保留 PINN、PINO、TwinMoE 正常执行的影子推理、路由、对比审计和发布门禁。
- 域内/域外/已适配判断、zero-shot/few-shot/shadow-fallback 路由和置信门。
- 电池短时工况孪生、证据、物理残差、安全投影和基线/候选比较。
- release gate、shadow release、外部锁箱和失败关闭规则。

明确分级：

- `standard` 模型只有 checkpoint、适配器、数据契约和评测同时通过时才显示“可用”。
- 跨域 SOH 的 0.194% 只能标记为 HUST 目标域 few-shot 结果；Oxford 新来源 2.708% 是更诚实的外部锁箱证据。
- SOC 神经校正目前增益有限且尚未证明跨电芯泛化，不能替换物理基线。
- PINN/PINO/TwinMoE 是正常启用的影子运行链，不是闲置资产；它们参与推理、路由、分歧比较和审计，生产主输出占比保持 0%。未完成实体 HIL、真实车队和发布批准时不得替换工程基线。

不迁移：论文生成、海量研究日志、训练期临时脚本、无运行价值的数据下载器、旧页面、`askInterpreter.ts` 等大型混合模块。

### 17.5 电池模型 ONNX 轻量化决策

**结论：可以轻量化，但必须逐模型迁移，不能为了 ONNX 破坏现有运行逻辑。** 当前制品均为 PyTorch/safetensors，没有现成 ONNX。首期以插件网关复用现有服务；标准模型优先导出，PINN/PINO/TwinMoE 只有在数值、路由、回退、门禁和证据完全等价后才切换运行时。

模型分级：

| 模型 | ONNX 可行性 | 首版策略 |
|---|---|---|
| SOCFormer | 高；主要是 Linear、Transformer Encoder、LayerNorm、Sigmoid 和位置编码 | 首批转换；固定窗口，动态 batch；CPU FP32 先通过等价门禁 |
| BMSFormer | 高；主要是 Linear、Conv1d、BatchNorm、LayerNorm、GELU 和 Einsum | 首批转换；为 Einsum/注意力建立独立数值等价样本 |
| BatteryMFormer | 中；模型输入、mask、条件 embedding 与 Python 后处理更复杂 | 第二批转换；建立固定 Tensor Contract，把格式处理和结果解释迁到 TypeScript |
| PINN/PINO/TwinMoE/SPM | 中低；图大、输出多、条件分支、路由和无扰切换复杂 | 保持现有影子运行链；并行做 ONNX/TypeScript 等价实验，未通过前不替换当前实现 |

导出与发布链：

```text
PyTorch checkpoint（离线）
  → inference wrapper（扁平 Tensor 输入输出）
  → ONNX opset 18 导出
  → onnx checker / shape inference
  → ONNX Runtime CPU 对比
  → 黄金数据逐样本与统计指标等价
  → 性能/内存测试
  → 签名模型 Manifest + SHA-256
  → production / shadow / candidate 发布门禁
```

具体规则：

- Python 仅存在于 `tools/battery-model-export` 或独立训练环境，不进入生产安装包。
- 数据格式识别、字段映射、归一化、窗口切片、物理基线、域判断和后处理统一迁到 TypeScript，并用同一黄金数据对 Python 原实现做合同测试。
- ONNX 模型只接收数值 Tensor，不接收文件名、CSV、业务对象或任意 JSON。
- 首版使用服务器/本地 API 的 `onnxruntime-node` CPU Worker；不把模型和 Runtime 打入普通浏览器首屏。
- 暂不做量化。模型本身体积较小，先保证 FP32 等价；只有基准证明收益明确且精度门禁通过后，再评估动态 INT8/FP16。
- Session 按模型版本懒加载并缓存；限制并发、输入点数、内存和执行时间；Worker 失败后清理 Session 并回退物理/统计基线。
- 模型 Manifest 必须记录模型 ID/版本、ONNX opset、输入输出 schema、预处理版本、来源 checkpoint 哈希、训练/验证域、指标、决策状态和生成时间。

ONNX 发布等价门槛：

- 固定黄金样本上，PyTorch 与 ONNX 的逐点误差和最终业务指标同时达标；容差按模型输出定义，不使用一个笼统误差覆盖 SOC、SOH 与 RUL。
- SOC/SOH/RUL 的置信门、域外回退和警告文本不得因 Runtime 替换而改变。
- ONNX 版本若未通过外部锁箱、异常输入和重复运行测试，只能作为 `shadow`，不能替换已发布基线。

2026-08-30 已把上述要求落为 `BatteryOnnxEquivalenceManifest` 和逐模型迁移门禁：三个正式模型必须分别提交与当前模型版本一致的 checkpoint/ONNX SHA-256、opset 18 FP32 制品信息、输入输出及前后处理合同、SOC/SOH/RUL 各自的黄金样本误差、边界/域外/非法输入和至少三次重复运行证据。`tools/battery-onnx/export_primary_candidates.py` 已从三个正式 checkpoint 生成候选制品并完成张量层等价：BMSFormer、SOCFormer、BatteryMFormer 最大绝对误差分别约 `8.9e-8`、`2.7e-7`、`7.2e-7`，5 次重复运行漂移均为 0。同一工具已回放 TEMPEST 280Ah/700 循环、工程 LFP 100Ah 和工程 NMC 58Ah 三套记录，共 9 个“模型×记录”比较全部通过。TEMPEST 上 BMSFormer 的 SOH/容量完全一致，SOCFormer 物理锚混合 SOC 最大差约 `7.6e-6` 个百分点，BatteryMFormer 的 5000 点 SOH 轨迹最大差约 `1.53e-5` 个百分点且 RUL 均为 2903 圈；工程 LFP/NMC 的 RUL 也分别一致为 2657/675 圈。BatteryMFormer 候选约 34.4 MiB，只允许服务端按需加载。

正式执行逻辑：`标准寿命专家先行 → 物理风险触发 PINN → 完整性/置信/分歧保护决定最终寿命专家`；`电热轻专家先行 → TwinMoE 动态风险路由 PINO → 域外或极高风险由 SPM 接管`。单个神经专家仍无权绕过路由直接覆盖结果；高分歧不做无依据平均，保留标准结果并标记人工复核。源服务原始字段完整保留，平台增加 `production-route` 决策证据；提交孪生状态时写入路由选中的轨迹，不再固定提交电热基线。

目录排除的只是 backup、smoke、epoch、ablation、损坏 checkpoint 和无运行调用点的实验模型。页面、API 和 MCP 必须能发现上述正式与影子核心能力，并始终显示 `outputAuthority`、`productionTraffic` 和发布门禁，避免把“正在运行”和“可控制生产”混为一谈。

#### E. Artifact 分级

本地 checkpoint 数量很多，但 checkpoint 不是新的产品模型家族。统一登记为：

- `production`：当前发布基线，满足来源、等价、锁箱和运行门禁。
- `shadow`：真实运行时参与比较但不能成为主输出。
- `candidate`：研究/评估使用，默认不加载。
- `archived`：历史版本、backup 和消融实验，只保留元数据、指标和哈希，需要时从模型仓库恢复。
- `quarantined`：例如名称含 `CORRUPTED-doNotUse` 的损坏 artifact，禁止加载、导出和复制到发布包。

`smoke`、`epoch1`、`ablation`、`backup` 不进入默认安装包。它们的实验记录仍可在模型中心追溯，但不能让用户误选为生产模型。

#### F. 模型中心页面

模型中心不是另一个复杂 AI 门户，只提供五个视图：

1. **任务视图**：SOC、SOH、RUL、多物理、Pack、域适配。
2. **模型视图**：模型家族、版本、输入输出、适用化学体系与运行状态。
3. **证据视图**：训练域、验证域、外部锁箱、最坏组、置信与已知限制。
4. **运行视图**：ONNX 加载、冷启动、延迟、内存、回退率、域外率与专家分歧。
5. **发布视图**：candidate → shadow → production → rollback，所有状态变化需要评测收据和审计。

任务工作台只调用 Capability ID，不硬编码模型名称。这样可以完整保留所有模型，又不会把算法复杂度甩给普通用户。

### 17.7 科学几何与多物理工具链取舍

这些框架只在能够补强“可信训练数据、物理校验或工程资产交付”时进入体系，不按框架数量建设产品菜单：

| 能力 | 决策 | 产品边界 |
|---|---|---|
| OpenCascade / Replicad | 已采用 | 在线参数化资产的精确几何与 STEP 交付；不再引入 PythonOCC 重复内核 |
| Gmsh + FEniCSx | 高价值候选 | 若分子元宇宙现有正式数据链确实依赖它们，则抽取为离线黄金数据、训练和验证流水线；不进入在线 SOC/SOH/RUL 推理路径 |
| Trimesh | 条件采用 | 仅在 CT/SEM 网格质量检查、修复和格式转换存在已证实缺口时作为离线适配器，不复制现有预览/优化能力 |
| CadQuery / build123d | 可选离线作者工具 | 最多选择一个用于复杂脚本化样本或工程模板生产，不进入主产品运行时 |
| NVIDIA Warp | 研究候选 | 仅用于有黄金样本和性能收益证据的 GPU 可微仿真实验，不替换现有确定性电热基线 |
| TRELLIS / TripoSR | 实验插件 | 用于外观资产和售前可视化草模；生成结果不得标记为 CT/SEM 科学重建、精确 CAD 或仿真几何 |
| PyVista、Mitsuba/Dr.Jit、CGAL | 暂不集成 | 当前主工程已有可视化/渲染/几何路径，尚无不可替代的生产缺口 |
| NeuroMesh / DeepXDE Geometry | 不按截图名称集成 | DeepXDE 可作为离线 PINN 工具评估；“NeuroMesh”需以真实仓库、调用点、checkpoint 和黄金样本证明其身份与生产价值 |

CT/SEM 多孔材料的正确工程链路应是：分割与标定 → 体素/点云 → 等值面提取 → 拓扑修复与单位校验 → Gmsh 体网格 → FEniCSx/FEM 黄金解 → PINN/PINO/TwinMoE 训练或外部锁箱验证。单图生成 3D 只能补视觉资产，不能替代这条科学链路。

引入门槛：先核对用户工程中的正式依赖、实际调用点、模型制品、许可证、黄金样本和发布脚本；只有仍在生产/影子运行并能复现结果的最小代码与模型进入主工程，其余保留为外部研究资产。

## 18. 页面与交互方案

### 18.1 一级工作区保持五个，AI 不成为孤立门户

在第 4.1 节五工作区基础上调整内容：

| 工作区 | 工业化后的核心内容 |
|---|---|
| 概览 | 交付阶段、关键风险、设备健康、调试通过率、运行异常、下一步行动 |
| 数据与资产 | 工程模型、工业资产、点位、数据集、语义对象、指标、模型和插件依赖 |
| 设计 | 2D 页面、3D 场景、拓扑、工程模型联邦、对象与数据映射 |
| 联动与自动化 | 行为、告警、问数、维护分析、仿真研究、虚拟调试和 AI 计划 |
| 校验与发布 | 数据/模型/插件/性能/权限/调试门禁、差异、审批、发布、回滚 |

AI 入口采用两层：

- 全局 `AI` 按钮用于跨项目搜索、解释和导航。
- 页面内“智能任务”根据上下文出现，例如“诊断此设备”“解释此告警”“生成调试用例”“询问此指标”“评估此电池”。

用户首先选择任务，不首先选择模型、Agent 或插件。

### 18.2 四个任务工作台

所有工作台使用同一结构，减少学习成本：

```text
对象与范围
  → 数据/模型就绪度
  → 计划与参数
  → 运行进度
  → 结果与证据
  → 建议行动
  → 保存为案例/报告/版本
```

1. **设备健康**：健康分不是主结论；首屏优先显示风险等级、主要证据、RUL 区间、数据质量和建议窗口。
2. **虚拟调试**：中心是信号/状态时间线与失败定位，3D 只承担空间定位和状态回放，不用视觉效果替代断言。
3. **可信问数**：先显示识别到的对象、指标、时间和口径；歧义时只要求最少澄清；结果可一键定位到场景对象和源数据。
4. **电池孪生**：生产基线与研究候选并列但视觉分级；域外、回退、置信区间和模型不可用必须比预测数值更醒目。

### 18.3 交互硬规则

- AI 永远先给结构化计划和依据，再给长文本解释。
- 结果面板固定显示来源、时间范围、插件/模型版本、置信度、决策状态和 trace ID。
- 所有建议行动支持“查看影响”，可写操作进入统一差异预览。
- 长任务支持取消、后台运行、重连和结果通知；关闭页面不丢任务。
- 插件不可用时给出明确降级路径，不出现空白卡片或无意义“AI 分析失败”。
- 专业术语旁提供短解释，但不把主界面写成说明书。

## 22. 最终架构判断

两项自研工程不应合并成一个新的巨型“AI 中心”。正确结构是：

```text
                        UI / SDK / REST / MCP
                                  ↓
                 Query + Command + Policy + Audit
                                  ↓
                 AI Orchestrator / Capability Registry
                    ↙             ↓              ↘
          Data Hub 查询      维护/调试插件       电池智能插件
            TypeScript         TS Worker          TS + ONNX
                    ↘             ↓              ↙
                     统一对象身份与 Evidence Contract
                                  ↓
       ApplicationDocument / Data Hub / Asset / Scene / Runtime
```

平台核心保持轻，领域能力可安装、可升级、可禁用、可替换；AI 负责理解、编排和解释，确定性程序负责数据、计算、验证和动作；BIM 负责工程空间与对象上下文；MCP 负责把已治理能力安全开放给外部 AI。这个边界能同时满足“简单、流程清晰、功能强大稳定”和“工业级但不大而全”。

2026-08-31 用户进一步确认补齐三个轻量核心，但仍保持上述边界：

3. **PD Lite**：建立轻量 PPR/BOP，覆盖工序、前置关系、资源分配、标准工时、版本、变更影响和方案对比；引用现有场景、对象、脚本和 Study，不建设 Teamcenter 式 PLM。

三项能力通过现有 2D、3D、脚本、运营和虚拟调试上下文进入同一 Study、版本和证据闭环，不增加一级导航。AI 只负责识别、编排和解释，关键路径、资源冲突、碰撞、时序和统计由确定性程序计算。

- WebGPU 已接入按需加载的 Three TSL `RenderPipeline`，覆盖 GTAO/SSAO 映射、对象轮廓、Bloom、景深、暗角、胶片颗粒、残影和 SMAA/FXAA；连续参数只更新 uniform，效果开关才重建节点图。旧的 WebGPU 包围盒伪轮廓已经删除，辅助网格只按后端线段覆盖率校准透明度，不改变模型材质和几何质量；当前完整效果同场景为 WebGL 260、WebGPU 316 draw call，P95 均为 7.2ms。

- 历史 WebGPU 长时采样曾在 80/960 样本时从约 19.7MiB 增至 52.8MiB，因此提前判失败，没有伪装成“仍在运行”。隔离实验确认 idle、对象引用、后处理和 JS 侧当前缓存不是主因；60 次整场替换的采样中，Three WebGPU `createBindings` 路径贡献约 21.92MiB 活跃分配，而公开 WebGPU `GPUBindGroup` 没有显式销毁接口。产品现按当前场景组件规模，在连续 12/8/4/2 次“完整场景替换”后自动重建同一 WebGPU renderer/device，并在加载遮罩内恢复快照；单对象编辑、动画、灯光、材质、极速发布标志和画质参数不受影响，也不降级 WebGL。120 对象的 101 次高频压力切换已完成 8 次回收，每次约 232–257ms，最终 P95 18.3ms、强制 GC 后堆约 25.4MiB；1000 对象的 12 次压力切换完成 3 次回收，每次约 839–865ms，最终 P95 7.4ms、堆约 26.8MiB，两组门禁均通过。该历史故障用于保留资源治理依据，不恢复已取消的 8 小时任务。
- 历史阶段曾执行 `verify:gpu-release` 并保留其资源回收分析；该快照的测试数、包体和源码数量不代表当前最终构建，本轮以最新独立门禁结果为准，且不恢复用户已取消的 WebGPU 长稳任务。
- WebGL 历史长时门禁完成 960/960 个采样周期，P95 7.4ms、最终 JS 堆 14.3MiB；该结果来自本批次早期构建，只作为稳定性旁证，不能代替最终构建的真实业务资产复验。
- 2026-08-30 曾启动最终构建的 8 小时 WebGPU 采样；用户随后取消该任务，因此不再等待完成，也不把未完成采样写成通过证据。
